## Hypothesis verdicts

- **H1: verified.** Loopback HTTP MCP with a per-run `OPENCLAW_MCP_TOKEN`, and no tool-call injection into the CLI protocol (claims 5, 26). The three modes form a closed union (1). Refinement: the default mode is `claude-config-file` (2), which injects `--strict-mcp-config --mcp-config` argv (3).
- **H2: verified.** `prepareExecution` returns env/clearEnv/beforeExecution/cleanup and an optional custom `execute` transport (8, 9). Caveat: it does not receive the private `authCredential` unless the backend is bundled (7).
- **H3: verified, with a nuance.** Non-Claude backends without `liveSession` share one global lane keyed by `backendId` when `serialize` is not `false` (17, 19). `serialize: false` gives a per-run key, meaning no core serialization at all. Per-owner keys need `liveSession`, whose only value is `"claude-stdio"` (10, 17, 18).
- **H4: verified.** Only an auth-profile credential of type `api_key`, `token`, or named `oauth` satisfies the boundary (20, 21). An opaque CLI login cannot (20).
- **H5: partly verified.**
  - The `resumeArgs`-replaces-`args` claim is verified (16, 32).
  - The `modelProvider` claim is **disputed** as stated. Omitting it does skip the provider-runtime binding, but only with a warning, not silently, and direct `cursor-cli/<model>` refs still work (14, 15).
  - The synthetic-auth / missing-auth claim is plausible but only partly verified (29, 30, 32). I did not trace the exact `resolveSyntheticAuth` versus `prepareSyntheticAuth` hook name.
  - The #148584 claim is verified as reported. It was closed "completed", but no merged fix PR was identified (31).

## Answers

1. **Type shapes.** Quoted in claims 1, 7-13 and 23 (`src/plugins/cli-backend.types.ts`).
   - `bundleMcpMode` is a closed union, and plugins cannot supply a materializer.
   - The `prepareExecution` ctx has no MCP URL or token field. It does get `env`, which holds `OPENCLAW_MCP_TOKEN`, plus `GEMINI_CLI_SYSTEM_SETTINGS_PATH` in Gemini mode (5, 6). In Gemini mode the settings file contains the concrete loopback URL and Bearer header (4). A plugin could therefore set `bundleMcpMode: "gemini-system-settings"` (args stay untouched, claim 3), read that file in `prepareExecution`, and write its own `.cursor/mcp.json` into a per-run or per-agent dir. This is an inference from code and is not tested. I did not verify that Gemini-mode server entries are a URL-plus-headers shape Cursor accepts.
   - `liveSession` is closed (`"claude-stdio"`).
   - `nativeToolMode` is `"none" | "always-on" | "selectable"`, and `toolAvailabilityEnforcement` is `"execution-args" | "prepare-execution"`.
2. **Verdicts.** See Hypothesis verdicts. For a per-session or per-agent queue on a third-party backend, core offers no such lane. The options are one global lane (`serialize: true`) or none (`serialize: false`, per-run key). With `serialize: false`, the plugin must do its own per-agent or per-session locking, for example in `beforeExecution` or a custom `execute` (8, 9, 17).
3. **Account boundary.** It is satisfied by an auth-profile credential: `api_key` with a key, `token` with a token, or `oauth` with `accountId`/`email` (20). The profile is selected explicitly or via `defaultAuthProfileId` (21, 23). `authEpochMode` only affects session-reuse invalidation, not history (23). For a subscription-login CLI, a plugin could declare `defaultAuthProfileId` pointing at a user-created `api_key` or `token` profile (e.g. a Cursor API key), which would authorize replay. An opaque `cursor-agent login` cannot (20). Whether the same key must also drive `cursor-agent` auth is not enforced by core. The boundary only fingerprints the profile credential. Separately, a fresh empty transcript is always allowed (22).
4. **Model catalog.**
   - The manifest `cliBackends` auto-loads the plugin, and `setup.cliBackends` exposes the backend to discovery cold (28).
   - Standalone backends without `modelProvider` remain selectable as direct refs; with `modelProvider` the backend becomes a runtime alias hidden from the provider picker (14).
   - In the #148584 repro, the catalog came from `models.providers.cursor-cli.models[]` config (31). Picker availability depends on auth evidence or synthetic auth (29).
   - I did not trace `resolveDynamicModel` or the provider `catalog` hook.
5. **Skills.** Non-Claude backends get OpenClaw's runtime skills catalog in the system prompt (`resolveCliSkillsPrompt` → `resolveRuntimeSkillsPrompt`), and skill paths are remapped in the prompt (24, 25).
6. **Changelog and #148584.** The changelog is split into `docs/releases/<version>.md` (`CHANGELOG.md` points to docs.openclaw.ai/releases). Relevant items are in claim 33; none change the `CliBackendPlugin` shape for third parties. For #148584, see claim 31.
