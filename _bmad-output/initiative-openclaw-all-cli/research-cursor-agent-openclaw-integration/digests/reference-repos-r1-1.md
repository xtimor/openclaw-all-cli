## Per repo

### jeehou/openclaw-cursor-cli (closest analogue, but stale and broken on current OpenClaw)
1. **Connection:** a native OpenClaw plugin that registers a provider and a CLI backend under the same id (claims 1, 2, 4, 5). It is the template our plugin would follow.
2. **Invocation:** `cursor-agent -p --output-format stream-json --stream-partial-output [--force --trust] [--mode] [--sandbox] --model <id>`, with the prompt as an argument (max 8000 characters). The host parses the output using the `claude-stream-json` JSONL dialect (claims 2, 3).
3. **Tools:** none of OpenClaw's tools reach the CLI. `nativeToolMode: "always-on"` means Cursor's own tools run, with `--force --trust` by default; `allowTools:false` or `mode: ask|plan` reduce them (claims 2, 3). There is no MCP or skills bridge.
4. **Sessions:** `sessionMode: "existing"` captures `session_id` and resumes with `--resume {sessionId}`; the system prompt is appended on the first turn only. Resume is broken (claim 6). The plugin itself does no history replay.
5. **Isolation and concurrency:** nothing in the plugin. There is no HOME or config-dir override and no cwd handling of its own (the host decides). It has no locks.
6. **Usage:** zero cost in the model definition; any token parsing is left to the host dialect. Whether the host reads Cursor's `usage` was not verified.
7. **Maturity:** abandoned since 2026-05. Three host-compatibility breakages are open: the plugin isn't loaded (claim 7), shows as missing auth (claim 8), and isn't bound to its CLI runtime on 2026.10.x (claim 9). Forks carry the fixes (claim 10).

### elvatis/openclaw-cli-bridge-elvatis
1. An OpenClaw plugin that runs an OpenAI-compatible proxy which OpenClaw reaches through the `vllm` provider. It does not use the CLI-backend API (claim 11).
2. Spawns each CLI with the prompt on stdin (to avoid E2BIG) and text or JSON output. There is no Cursor support (claims 12, 14).
3. Tool bridging by prompt injection: a JSON tool protocol is parsed back into OpenAI `tool_calls`, so OpenClaw executes the tools. The CLI's own tools are *not* disabled (`--dangerously-skip-permissions`). Skills are injected into the prompt as paths to SKILL.md (claims 13, 14).
4. Every call is fresh; resume was removed after stale-session failures. Truncated history is replayed every turn (claim 15).
5. Minimal env, neutral cwd (home or tmp), and per-session tmp workdirs in its long-running session manager. No per-agent HOME. No slot or queue logic was found (claim 16).
6. Real usage when the CLI reports it, otherwise an estimate (claim 17).
7. Low activity since 2026-07; the issues are only dependabot (claims 18, 19).

### drewstone/cli-bridge
1. A standalone OpenAI-compatible server, not OpenClaw-specific. It treats OpenClaw as one of its *backends* over ACP (claim 20). No Cursor.
2. Claude: `--print --input-format stream-json --output-format stream-json --verbose` (or `-p <text>`), plus `--effort`, `--system-prompt`, `--mcp-config`, and `--setting-sources project,local` (claims 24, 26).
3. The CLI runs its own tools; MCP servers are passed through per request, and tool_use events are surfaced rather than turned into client-executed `tool_calls` (claim 26).
4. A SQLite table maps external session ids to internal ids, `--resume` uses the internal id, and the session is bound to its first-turn profile and model. "Portable context transfer" can import history into a fresh native Codex session (claim 21; README §Portable context transfer).
5. A per-session turn lane (409/429), host admission slots with lanes and a reconciler, per-session `--session-dir` or per-run HOME where the CLI supports it, one process per Codex account, and an optional fs-jail or Docker executor (claims 22, 23, 25).
6. Normalized token usage, with explicit `cost_known` provenance (claim 27).
7. Very active; self-described personal tool; heavy design (claim 28).

### verivus-oss/llm-cli-gateway
1. An MCP server exposing per-provider request tools; Cursor is "maintain-only" (claim 29). It is not an OpenAI API or an OpenClaw provider.
2. Default `cursor-agent --print` text output, which buffers until exit; stream-json is opt-in. Its parser is the best documentation of Cursor's stream-json wire format (claims 30, 31).
3. No tool bridging into the CLI; the gateway itself *is* the tool surface for the calling client. It reports `toolCalling: true` for Cursor's native tools (claim 29).
4. Uses real Cursor chat ids with `--resume <chatId>` or `--continue`; gateway `gw-*` ids are never passed as resume ids (claims 32, 33).
5. Worktrees per session, a workspace allowlist, the `--workspace` vs cwd distinction, and spawn-env scrubbing; durable jobs in SQLite or Postgres (claims 33, 34).
6. Parses Cursor `usage` (input, output, cacheRead) from the result event (claim 30).
7. Mature engineering signals, low adoption (claim 35).

## Patterns

- **Two integration shapes recur.** One is a native OpenClaw CLI backend (jeehou); the other is an OpenAI-compatible proxy behind a generic provider (elvatis via `vllm`; drewstone, agent-cli-to-api, cursorcli2api, and opencode-cursor in other hosts). MCP-server gateways (verivus) are a third shape that inverts control: the client delegates to the CLI. elvatis avoided the CLI-backend API without saying why. drewstone and verivus are host-agnostic by design.
- **Who owns the tool loop.** Only elvatis makes the *host* run tools, and only through fragile prompt-injected JSON. Everyone else lets the CLI run its own tools, sometimes with MCP passthrough (drewstone). opencode-cursor's README singles out oakimov/cursor-opencode-provider as the project where "OpenCode owns the tool loop" by speaking Cursor's native agent protocol, which is the approach closest to our goal (claim 36).
- **Mapping external to native resume ids** is universal where resume exists (drewstone's table, verivus separating `gw-*` from chat ids, jeehou's `sessionIdFields`). Nobody passes the host's id as the CLI id.
- **Resume is fragile.** elvatis dropped it entirely after stale-session errors and SIGTERM-corrupted sessions (claim 15); jeehou's resume never worked headless (claim 6). drewstone binds the session to its first-turn profile and model to avoid mismatched resumes.
- **Isolation through the CLI's own config dir rather than a fake HOME** where possible: drewstone uses `--setting-sources` and avoids `--bare` because of OAuth (claim 24), and keeps one process per account for Codex. elvatis found a minimal env breaks keyring OAuth unless XDG/DBUS vars pass through (claim 16). Overriding HOME is used only where the CLI's auth survives it (Prime).
- **Per-session serialization plus a global slot cap** (drewstone) is the only explicit concurrency design; the others have none.
- **Stream-json is required** for incremental output and for capturing `session_id` and `usage` from Cursor (claims 30, 31).

## Leads

- **OpenClaw host contract drift:** `modelProvider` on the backend (2026.10.x), `syntheticAuthRefs` plus `resolveSyntheticAuth`, the startup-load filter for `api` values, and `resumeArgs` replacing `args`. Verify each in OpenClaw source or docs, and read host issue openclaw/openclaw#148584 (claims 6–9).
- **The DonnieFi fork (0.0.10)** and the Ryxwaer and daswass forks probably carry the resume, auth, and binding fixes. Fetching DonnieFi's `index.js` from `main` returned nothing; try other branches or tags.
- **oakimov/cursor-opencode-provider:** a host-owned tool loop over Cursor's native agent protocol, most aligned with "OpenClaw owns the turn". Also `@cursor/sdk` (used by opencode-cursor) as an alternative to spawning the CLI.
- **`cursor-agent acp`:** a native ACP server (claim 32). ACP may give per-turn tool and permission callbacks; check whether OpenClaw's ACP support could drive it.
- **No source here isolates Cursor's own state:** whether `cursor-agent` honors a config-dir env var (for example `CURSOR_CONFIG_DIR`), where chats are stored, and whether two concurrent runs sharing the CLI home collide.
- **Contradiction to resolve:** jeehou feeds Cursor output through the host's `claude-stream-json` dialect, but verivus documents Cursor-specific events (`thinking/delta`, `tool_call` with `<name>ToolCall`) and camelCase usage keys. It is unknown whether the host parses Cursor's `result.usage` or `tool_call` events correctly.

## Not found
