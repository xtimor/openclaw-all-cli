# Agent identity

Who the issue agents write as. With the relay on, GitHub shows `<app-slug>[bot]` on their comments, labels, and pull requests; with it off they act as the owner through the GitHub connector, as before. Agent-neutral; used by [triage.md](triage.md), [implement.md](implement.md), and [comments.md](comments.md). The same idea files issues in OpenClaw's repository: [Upstream issues](#upstream-issues). Design: `_bmad-output/initiative-openclaw-all-cli/epic-distribution/issue-flow.md`.

Why a relay: a cloud session's proxy swaps the owner's credentials into every `api.github.com` request, so an agent in a session can only write as the owner, and going around the proxy is not allowed. From a session, `gh workflow run`, `gh run watch`, `gh run list`, and reads work; repository settings (Actions variables and secrets) and run logs are refused. So the agent does not hold the app's key. It dispatches the `Agent write` workflow (`.github/workflows/agent-write.yml`) with a list of operations; the workflow mints the app's token from an environment secret and `scripts/agent-write.mjs` applies the operations as the app, with its own guards. Reads stay as they are (any tool, as the session). The agent reads every effect back by REST; it cannot read the relay's log.

## For the agents

At the start of a run, before any GitHub write.

1. **Is the relay on?** The repository file `.github/agent-identity.json` on `main` says: `{"login": "<app-slug>[bot]"}`. Read it from `main`, not from your branch:

   ```bash
   gh api 'repos/xtimor/openclaw-all-cli/contents/.github/agent-identity.json?ref=main' --jq .content | base64 -d | jq -r '.login // empty'
   ```

   - A login (`<slug>[bot]`): the relay is on; that login is `ME`. Continue with step 2.
   - 404 (no file), or an empty or missing `login`: no relay. Keep the owner connector, set `ME` as your instructions say (the connector's "get me" call, or `gh api user`), write directly as before, and put "acting as the owner (no agent app configured)" in your report. Skip to step 4.
   - Any other answer (no answer, 403, a file that is not JSON, a login that does not end in `[bot]`): stop and report; do not guess.
2. **From here a failed relay stops the run; it never falls back to writing as the owner.**
3. **Write through the relay.** Collect the writes of one step into one JSON list and write it to a file under `/tmp` with the Write tool (not a shell heredoc or function, no ad hoc wrapper scripts: the session's permission check denies those). Then run exactly this, from the repository root, as the whole call: nothing before it (no `cd ... &&`, no environment prefix, no absolute path, no pipe) and nothing after it (no `;`, `&&`, `||`, pipe, redirect, or follow-up read such as `gh api` in the same call), one call per dispatch:

   ```bash
   scripts/agent-relay.sh /tmp/agent-ops-<n>.json
   ```

   The allow rules in `.claude/settings.json` match only that command shape (`scripts/agent-relay.sh <file>`); any other shape is not allowed and a refused call stops the run. On 2026-10-27 a run chained the relay with a direct `gh api` write in one call; the permission check refused the whole call as an external write and nothing was applied. Read the effects back in separate calls after the dispatch.

   The script (`scripts/agent-relay.sh`, the only relay entry point the repository's `.claude/settings.json` allows) dispatches `agent-write.yml` on `main` with the file's text, watches the run, checks that it concluded `success`, and prints the run id. It waits until the run is `completed` (polling every 10 s for about 20 minutes after `gh run watch`). It exits non-zero with a one-line reason on stderr when the file is missing, not a JSON array, or over 60 000 bytes (exit 2, nothing dispatched; split the step), the dispatch fails, no run id comes back, the run did not succeed (`relay run <id>: <conclusion>`), or it is still running after the wait (`relay run <id> still <status>; do not re-dispatch, read back first`: then read the effects back by REST and dispatch only what is missing). Treat a non-zero exit as: stop the run and say what failed in your report, after the read-back below. It never touches the proxy variables.

   If your `gh` prints no run URL (an older version), the script stops with "no run id"; list the runs instead and take the newest `workflow_dispatch` run created after the dispatch: `gh api 'repos/xtimor/openclaw-all-cli/actions/workflows/agent-write.yml/runs?event=workflow_dispatch&per_page=5' --jq '.workflow_runs[] | [.id, .created_at, .actor.login] | @tsv'` (the actor is the owner).

   **Read every effect back by REST** (step 4), whether the run succeeded or not: the comment by `ME` on the issue, the issue's labels and state, the pull request by head branch (`gh api 'repos/xtimor/openclaw-all-cli/pulls?head=xtimor:<branch>&state=all'`), its draft and merged state. **Never repeat operations that a failed run may have applied without reading back first**, and then dispatch only what is still missing. Rules:
   - **One dispatch per issue step**, and the next only after the previous run has finished. Runs do not queue safely when two are pending.
   - **Comment and its labels go in the same dispatch**, comment first: operations apply in order, so the state automation sees the comment before the label change. A failure stops the list; later operations are not applied.
   - The text of every operation is public the moment you dispatch it (workflow inputs are readable by anyone who can read the repository), like the comment itself. Put no secret, token, or environment in it. The workflow echoes no body.
   - The branch of a `pr_create` is pushed first with `git push` from your session (that is git, not the API; the session's own git access is used).
   - Only the owner can dispatch, and only the first attempt of a run counts: the relay refuses another dispatcher, a different person who re-runs a run, and any re-run. A refused list applies nothing.

   Operations (`scripts/agent-write.mjs` validates the whole list first; at most 50 operations and 60 000 characters):

   | Operation | Fields | Guard in the relay |
   | --- | --- | --- |
   | `comment` | `issue`, `body` | none |
   | `edit_comment` | `comment_id`, `body` | the comment's author must be the app |
   | `labels` | `issue`, `add`?, `remove`? | only `status:`, `type:`, `priority:`, `source:` names in lowercase (`status:[a-z0-9-]`); `status:approved` and `status:upstream` are never added (the first is the owner's, the second is the `Upstream post` workflow's); `status:awaiting-post` may be; no name in both lists; adds first, then removes; removing a label that is not set is fine |
   | `close` | `issue`, `reason` (only `not_planned`) | agents never close an issue (owner decision 2026-10-28; they use `status:declined` or `status:needs-info`). The one exception is a security report: the same list must post the exact `SECURITY_CLOSE_COMMENT` (printed in [triage.md](triage.md#security-report)) on that issue, in a `comment` before the `close`. Otherwise the whole list is refused, nothing applied. An issue, never a pull request |
   | `reopen` | `issue` | an issue, never a pull request |
   | `pr_create` | `head`, `title`, `body`?, `draft`? | `head` must be a `claude/` branch of this repository; base is `main` |
   | `pr_ready` | `pr` | the pull request's author must be the app |
   | `pr_edit` | `pr`, `title`?, `body`? | the pull request's author must be the app |
   | `pr_close` | `pr` | closes only an open draft pull request by the app, head branch `claude/` in this repository, title exactly `Issue batch (in progress)`, not updated for 2 hours or more (an idle batch; see [implement.md](implement.md#before-the-batch)), **and** whose plan files (`_bmad-output/**/*-plan.md` among its changed files, read at its head) include none at status `done` or `built`, unless another open `claude/` pull request of the app already contains its head (the run resumed it on its own branch). The idle, author, title, and plan checks run on every `pr_close` of the list **before any operation is applied** (a `comment` or `pr_edit` earlier in the same list refreshes the pull request's update time, so checking at the close would always refuse a one-dispatch retire); the carrier is looked for at the close, after an earlier `pr_create`, and the pull request must still have the head that was checked. Anything else is refused |
   | `merge` | `pr`, `sha` | kept for completeness; agents do not use it (GitHub's `Batch merge` workflow merges the batch pull request, see [implement.md](implement.md#merging-the-batch-pull-request)). Method `merge`; refused unless the pull request is open, not a draft, by the app, head branch `claude/` in this repository, base `main`, title starting `Issue batch`, head sha equal to `sha`, mergeable state `clean`, the check run named `check` (run by GitHub Actions) present and `success` on that sha, every other check run completed `success`, `skipped`, or `neutral`, and the combined commit status not `failure`/`pending`/`error` (no statuses at all is fine) |

   Example, a triage decision (comment, then labels, in one run):

   ```json
   [
     {"op": "comment", "issue": 12, "body": "<!-- issue-triage -->\n**Status:** ..."},
     {"op": "labels", "issue": 12, "add": ["type:bug", "status:triaged"], "remove": ["status:new"]}
   ]
   ```

   The relay's `merge` operation and the `Batch merge` workflow (`.github/workflows/batch-merge.yml`, `scripts/batch-merge.mjs`) share the same guards (`checkMergeable` and `checkGreen` in `scripts/agent-write.mjs`). Agents never dispatch `merge`: the routine's permission check refuses an agent's merge of its own pull request, so the agent marks the batch ready (`pr_edit`, `pr_ready`) and `Batch merge` merges it as the app when it is green. Beyond the guards the relay does not judge: whether a comment is right, or which issue to close, is yours.
4. **Read authors and actors by REST.** `gh pr view --json author` and `gh issue view --json comments` use GraphQL, where an app shows under another name than `<slug>[bot]`. For every check of who wrote or did something, use `gh api` and compare the REST login with `ME`: a pull request's author `gh api repos/xtimor/openclaw-all-cli/pulls/<n> --jq .user.login`; a comment's author `gh api repos/xtimor/openclaw-all-cli/issues/<n>/comments --paginate` (`.user.login`, `.created_at`, `.body`); an event's actor `gh api repos/xtimor/openclaw-all-cli/issues/<n>/events --paginate` (`.actor.login`). Other reads may use any tool.
5. Never print, log, commit, or paste a key, a token, or a JWT. You hold none: the relay does. No `env`, `set -x`, or `gh auth status` output in a report either.

### Your comments

"A comment of yours" (what the prompts call a comment of `ME`) is a comment whose first line is your marker (`<!-- issue-triage -->` or `<!-- issue-impl -->`) and that is, by REST:

- by the app login;
- with the relay on, by an owner (`ISSUE_FLOW_OWNERS` in `.github/workflows/issue-flow.yml`) **and created before the app's first marker comment on that issue** (earlier runs acted as the owner);
- with the relay off, by the owner.

An owner's comment after the app's first marker comment on that issue is never yours, marker or not. `ME` itself is the app login (or the owner with the relay off); the batch pull request's author check is `ME`.

## Upstream issues

An agent in a session cannot write to `openclaw/openclaw` either: the proxy swaps the owner's session credentials, which are scoped to this repository, into every `api.github.com` call, and attaching the repository with push access was refused. The owner stored a personal token as the secret `GH_PUBLIC_TOKEN` in the GitHub Environment `agent` instead. No session holds it. Two workflows use it, both through `scripts/upstream-issue.mjs` (one code path, one set of guards), and both publish as the owner (the issue or comment shows the owner's login, not the bot):

- **`Upstream post`** (`.github/workflows/upstream-post.yml`, `scripts/upstream-post.mjs`, ticket 3.25): the agents' way. The agent writes a draft, the owner's label `upstream:post` on our issue is the approval, GitHub publishes it, the way `Batch merge` merges on the owner's "ready". The routine's auto-mode permission check refuses a public write under the owner's name made by the agent itself (2026-10-29: it refused `scripts/upstream-issue.sh` although the command was on the allow list), so agents never make that call.
- **`Upstream issue`** (`.github/workflows/upstream-issue.yml`, `scripts/upstream-issue.sh`): a dispatch by hand, for the owner's own interactive sessions. Agents do not use it.

**When.** Only (1) when the outcome of an issue you are building needs a change in OpenClaw **and the owner approved that issue** (`status:approved` set by an owner, checked as in [implement.md](implement.md)), or (2) when the owner asks, which means the owner approves the issue of ours that the upstream text serves first. The workflow enforces this (see below): without an owner's `status:approved` on that issue it publishes nothing. Triage writes no draft (nothing is approved yet). One draft per need. You write the draft and stop: you never publish it and never add the label.

**Draft and label (agents).** Put exactly one draft block in your `<!-- issue-impl -->` comment on our issue (the shape of [comments.md](comments.md), written through the relay as usual). The tags stand alone on their own lines; the text between them is the public text, **without** the `Filed for` line, which the workflow appends. One of these two forms:

```
<!-- upstream-draft target=openclaw/openclaw#<n> op=comment -->
The comment, in Markdown.
<!-- /upstream-draft -->
```

```
<!-- upstream-draft target=openclaw/openclaw op=create -->
Title: one line, at most 256 characters

The issue body, in Markdown.
<!-- /upstream-draft -->
```

`op=comment` posts a comment on the owner's own issue `openclaw/openclaw#<n>` (the target needs the number); `op=create` opens an issue (no number in the target; the first line is `Title: `, the body follows). For a create, follow the target's issue form headings (read them from `.github/ISSUE_TEMPLATE/` in `openclaw/openclaw`; when you cannot, use `### Summary`, `### Steps to reproduce`, `### Expected behavior`, `### Actual behavior`, `### OpenClaw version`, `### Additional information`). Everything in the block is public: no secret, token, or environment, and no issue text you were not meant to republish. In the same dispatch as the comment, set `status:awaiting-post` (not `status:blocked`: that is for the owner's decisions) with `Waiting for: @<owner-login>: review the draft and add upstream:post`. The owner reads the draft in your comment and adds the label `upstream:post` to our issue with their own click in GitHub. Write for these checks:

- The block is in the **latest** `<!-- issue-impl -->` comment by the app on that issue (an older one, a triage comment, and any comment by someone else are never read). When you post a new `<!-- issue-impl -->` comment, repeat the block in it. One block per comment and one comment per label: a second target issue needs a new draft after the first is published.
- The comment is **not edited within 60 seconds before the owner adds the label, or after it**: the workflow compares the comment's last edit with the time of the label event and refuses the draft otherwise (the owner waits a minute after your last edit and labels again). Leave the comment alone from your last edit until the result comment appears.
- **One comment (or issue) per target and round per issue of ours.** A draft for a target that this issue of ours already published for (the same `Filed for` line, round included, on that upstream issue, or the same title for a create) posts nothing new: the result comment names the existing URL (`**Existing:**`). A reply written after a publish, in a new `<!-- issue-impl -->` comment, is the next round (below). A second new issue for the same need needs a new, owner-approved issue of ours; do not redraft it here.
- The tags are exactly as above. A line that mentions `upstream-draft` in any other shape, a second block, an unknown attribute, or another op refuses the draft.
- A comment draft **names its target in the visible text** of the same comment, outside the tags and outside any HTML comment (for example a line `**Draft for:** openclaw/openclaw#<n>` above the block; the URL form works too, the number must match exactly), because the tag is invisible when the owner reads the comment and they must see where it goes.
- The text holds **nothing the owner cannot see**: no HTML comment (`<!--`) and no invisible or direction-changing character (zero-width, soft hyphen, bidi marks, the Unicode tag block). The owner approves the draft as rendered, so the workflow refuses hidden content: also no link reference definition line (`[label]: url`, which renders as nothing; write links inline), no raw HTML (a `<` followed by a letter, `!`, or `?`) outside a code span or fence, and no Unicode format character (`\p{Cf}`), variation selector, or invisible filler (so no zero-width joiner or emoji variation selector: write emoji without them).

What the workflow does (`scripts/upstream-post.mjs`, on the `issues` `labeled` event of `upstream:post` only): it changes nothing for a re-run (attempt over 1), a triggering actor who is not an owner, or a label that is already off again. Otherwise it refuses unless the person who added the label is an owner (`ISSUE_FLOW_OWNERS`), is a person and not a bot, and is the run's actor; reads the label event from the issue's events and refuses unless it is **the owner's own click** (by the person who added the label, an owner, `actor.type` `User`, and with no `performed_via_github_app`: a Claude session writes with the owner's login but shows an app such as `claude`, so an injected session cannot publish by adding the label), and takes that event's time as the label time; reads the draft as above (author: the login in `.github/agent-identity.json`, type `Bot`; with no login there no app is configured and nothing is trusted); builds the input of `scripts/upstream-issue.mjs` from the block plus the line `Filed for xtimor/openclaw-all-cli#<n>` and runs that script's own `run()` with `GH_PUBLIC_TOKEN`, so every guard below applies unchanged; then, whatever the outcome, posts one comment on our issue that starts with `<!-- upstream-post -->` and holds the published URL (or the refusal reason, which says to fix the cause and add the label again) and removes the label. If no result comment comes within a few minutes, the run was dropped (one pending run waits per group) or failed: the owner removes the label and adds it again. Read the result comment (REST) in your next run. After a post that was just made (created or commented) the same run, once the result comment is posted and the label removed, moves the issue to `status:upstream` with the job token: it adds that label and removes every other `status:*` label of the issue. The result comment's `Status:` line says what the run does (`status:upstream`, or `unchanged` for a closed issue, an unreadable issue, an `existing` result, or a refusal); a failed move turns the run red with the reason. An `existing` result posted nothing new, so it changes no status either (the issue may hold a newer draft in `status:awaiting-post`). A refusal changes no status: the issue stays `status:awaiting-post`, the result comment says `Status: unchanged`, and the owner fixes the cause and labels again, or approves the issue again so the agent rewrites the draft. The relay refuses `status:upstream` for agents (only the workflow knows a draft was published), and the state automation treats both new statuses like any other (the latest wins); neither is closed by the stale job, the owner closes the issue when upstream settles. Agents never close it.

**Later replies on the same target (ticket 3.26).** While an issue is `status:upstream`, every run reads the upstream thread ([implement.md](implement.md#watch-upstream)); when it asks for an answer the agent writes a new draft in a **new** `<!-- issue-impl -->` comment and sets `status:awaiting-post`, and the owner labels `upstream:post` again. The rule "one comment per target per issue of ours" then holds per marker and round: a reply carries `Filed for xtimor/openclaw-all-cli#<n> (reply 2)` (no suffix is round 1), and the shared path returns an existing comment only for the same marker **and** round. The round is read from the upstream thread itself, never from our issue: the workflow passes the creation time of the draft comment to `run()` of `scripts/upstream-issue.mjs` (the option `replyBefore`), and the round is one plus the number of comments by the token's user on the target whose marker line names this issue of ours (any round) and were created before that time. So a round 1 posted by the dispatch workflow counts, a result comment that is missing, failed to post, or was edited changes nothing, the same reply labeled again after it was posted has the same round and returns the existing comment, and a reply written after a post is the next round. An agent cannot write upstream, so it cannot change the count; it never chooses the round: a `round=` attribute and a `Filed for` line inside the draft are refused, and so is any `(reply N)` in the input of the dispatch workflow or in an environment variable (only the workflow's own call passes the option). A create draft keeps its single marker (no round). At most 98 earlier comments; every other guard stays as it is.

**Dispatch by hand (the owner's sessions).** Write the issue as JSON to `/tmp/upstream-issue-<n>.json`, then run exactly this as the whole call (nothing before or after it, as for the relay):

```bash
scripts/upstream-issue.sh /tmp/upstream-issue-<n>.json
```

The file is one JSON object: `{"title": "...", "body": "...", "labels": ["..."]}`; `labels` is optional (GitHub silently drops labels that someone without triage rights on the target sets; the run log, which only the owner can read, says which were applied, so read the new issue's labels by REST if they matter), `repo` is optional and can only be `openclaw/openclaw`. The body follows the target's issue form headings (read them from `.github/ISSUE_TEMPLATE/` in `openclaw/openclaw`; when you cannot, use `### Summary`, `### Steps to reproduce`, `### Expected behavior`, `### Actual behavior`, `### OpenClaw version`, `### Additional information`) and has exactly one line `Filed for xtimor/openclaw-all-cli#<n>` (the issue of ours it serves). Everything in it is public: no secret, token, or environment, and no issue text you were not meant to republish. The script prints the issue's URL on stdout (stderr says `created` or `existing`) and exits non-zero with one line on stderr when the dispatch fails, the run does not succeed (`run <id>: <conclusion> (<reason>)`), or the result cannot be read. Dispatching the same file again is safe: the script returns the issue it already filed (same marker line or same title, any state, among the owner's issues in the target) instead of a second one. When stderr says `existing`, check that it is the issue you meant: an older issue with the same title, even a closed one, is returned too, so give a new report a new title. One dispatch at a time (a second one waits; a third replaces the pending one and the helper reports `cancelled`).

What the workflow enforces, in `scripts/upstream-issue.mjs`: only `openclaw/openclaw` (a constant in code), the dispatcher and the person who started the run are in `ISSUE_FLOW_OWNERS`, attempt 1 only, it runs only on `main` in the `agent` environment, a title of at most 256 characters on one line, a body of at most 30 000, the whole input at most 40 000, at most 5 labels, exactly one `Filed for xtimor/openclaw-all-cli#<n>` line, and nothing is sent when any check fails. Two more guards (security review of ticket 3.23): the issue `#<n>` of ours must exist, be an issue (not a pull request), and have had `status:approved` labeled by an owner at some point, as the owner's own click (`actor.type` `User`, no `performed_via_github_app`: an approval made through an app, such as a Claude session acting with the owner's login, does not count; the `Issue flow` automation reverts it too) (read from its events with the job's own read-only `GITHUB_TOKEN`, `issues: read`; the owner's token never goes to our repository, the job token never goes upstream), so a changed marker number cannot file anything; and a new issue is refused when 3 or more issues by the token's user were created in the target in the last 24 hours (an issue already filed is still returned, so a retry works). It creates an issue or posts a comment, and nothing else: no edit, close, reopen, or label upstream. The token comes only through `env`, is masked, and appears in no log, summary, or output. The outcome is left as the run's last annotation, which the helper reads by REST.

**Comments.** Both workflows can post one comment on an issue the owner opened in `openclaw/openclaw`, for example the repro or retest a stale report waits for. A draft block does it with `op=comment` and `target=openclaw/openclaw#<issue>`. For a dispatch by hand write `{"op": "comment", "issue": <number in openclaw/openclaw>, "body": "...\nFiled for xtimor/openclaw-all-cli#<n>"}` to the same kind of file and make the same call as above (the body rules and the `Filed for` line are the same; `repo` is optional; a comment takes no `title` or `labels`, and a create takes no `issue`). Everything in it is public, as above. The script prints the comment's URL (it ends in `#issuecomment-<id>`) and stderr says `commented` or `existing`. Guards on top of the ones above (`scripts/upstream-issue.mjs`, ticket 3.24): the `Filed for` issue of ours is owner-approved, as for a new issue, and its title or body names the target issue as `openclaw/openclaw#<issue>` or `https://github.com/openclaw/openclaw/issues/<issue>` (the number matched exactly, so `#1729` is not `#172969`; one approval allows comments only on the upstream issues that issue names, so name every target in the issue of ours before you comment); the target issue exists, is not a pull request, and was opened by the token's user, so it never comments on someone else's issue; a comment by the token's user on that issue that already carries the same `Filed for` line is returned, not repeated (so a target issue gets one comment per approved issue of ours; a second note needs its own approved issue or a human); and a sixth comment in 24 hours by the token's user across the target is refused (counted on the user's own issues there). It posts one comment and never edits, closes, reopens, or labels. A failed run: read the target issue before dispatching again.

**Owner setup.**

1. Create a personal access token for the account that should author the upstream issues: a classic token with the `public_repo` scope, or a fine-grained token with Issues read and write on the target repository if its owner allows it. Nothing else.
2. Add it as the Environment secret `GH_PUBLIC_TOKEN` of the environment `agent` (the one that already holds the relay's key; deployment branches: only `main`): `gh secret set GH_PUBLIC_TOKEN --env agent` and paste the token. No repository-level secret.
3. Check it only with a real case: approve the issue of ours that needs the upstream change (`status:approved`), let the agent write its draft (see above), read it in the agent's `<!-- issue-impl -->` comment, and add the label `upstream:post` to that issue yourself (the label exists after the `Labels` workflow has synced `.github/labels.yml` on `main`). The `Upstream post` workflow publishes it, comments the result on the issue, and removes the label; take the label off before it runs to cancel. Every run publishes a real, public text upstream; there is no dry run, so do not test with a throwaway marker. Agents never add this label (the relay refuses it, and it is your approval). An agent session that acts with your own login through the GitHub connector shows an app on its label event (`performed_via_github_app`, for example `claude`), and the workflow refuses such a label and removes it, as it does for `status:approved`: both must be your own click in GitHub.
4. Optional, for your own interactive sessions only (agents do not call the helper): add it to the allow list of `.claude/settings.json` (agents must not edit it), next to the relay's rules. To publish by hand instead of with the label, run Actions, Upstream issue, Run workflow on `main`, or the helper, with the issue's real title, body, and marker:

   ```json
   "Bash(scripts/upstream-issue.sh *)",
   "Bash(bash scripts/upstream-issue.sh *)",
   "Bash(./scripts/upstream-issue.sh *)"
   ```

Rotate the token by replacing the secret and revoking the old token in your GitHub settings. If it leaks, revoke it there at once.

## For the owner

One-time setup (about 10 minutes):

1. GitHub, Settings, Developer settings, GitHub Apps, New GitHub App. Name it (the slug becomes `<slug>[bot]`). Webhook off. Repository permissions: Contents read and write, Issues read and write, Pull requests read and write, Checks read, Commit statuses read, Metadata read. Under "Where can this app be installed", choose "Only on this account" (that limits who may install it; the installation itself is step 2).
2. Install the app on `xtimor/openclaw-all-cli` only (Only select repositories).
3. On the app page, Generate a private key (a `.pem` file downloads). Note the App ID.
4. In the repository, Settings, Environments, New environment `agent`. Under Deployment branches and tags choose "Selected branches and tags" and add `main`. Add the environment secret `AGENT_APP_PRIVATE_KEY` with the text of the `.pem` file as it is (`gh secret set AGENT_APP_PRIVATE_KEY --env agent < key.pem` does it) and the environment variable `AGENT_APP_ID` with the App ID. No repository-level secret or variable is needed. The environment is what keeps the key from a copy of the workflow file on another branch: a run on any other ref cannot use it.
5. Delete the `.pem` file from your machine. Do **not** put the key in the routine's cloud environment: the agents never hold it.
6. Check the relay: dispatch `Agent write` by hand (Actions, Agent write, Run workflow, on `main`) with `[{"op": "comment", "issue": <an open issue>, "body": "relay check"}]`. The comment shows the bot; the run's summary names it (`Acting as <slug>[bot]`).
7. Switch the agents to the relay: add `.github/agent-identity.json` on `main` with `{"login": "<slug>[bot]"}` (you, or an agent session at your request, in a pull request or a commit), and put the same login in `ISSUE_FLOW_AGENTS` in `.github/workflows/issue-flow.yml` (for example `ISSUE_FLOW_AGENTS: "my-agents[bot]"`; comma separated).
8. Run the routine ("Run now") and check that its comments show the bot.

What changes: the agents' comments, labels, and pull requests are the bot's. The bot is not in `ISSUE_FLOW_OWNERS`, so the state automation treats it like any non-owner: an app-set `status:approved` is reverted (and the relay never adds it). `ISSUE_FLOW_AGENTS` has a narrower job: an agent's marker comment (`<!-- issue-triage -->` / `<!-- issue-impl -->`) never counts as the author's reply, which matters when the app itself opened the issue. Events made with an app token start workflows (unlike `GITHUB_TOKEN`), so `Issue flow` and CI run for the agents' labels, closes, comments, and pull requests like for a person's.

What the relay enforces, in `scripts/agent-write.mjs`: the dispatcher and the person who started the run are in `ISSUE_FLOW_OWNERS` of `agent-write.yml` (keep it equal to `issue-flow.yml`'s), the run is attempt 1 (no replays), it runs only on `main` in the `agent` environment, at most 50 operations and 60 000 characters, nothing is applied when any operation is refused, application stops at the first failure, and the per-operation guards in the table above (including green checks for a merge, which agents do not use). The private key is not passed to the script that handles the operations, and the token is revoked when the step ends. The agents still check before they dispatch (merge rules, who wrote what).

The `Batch merge` workflow (`.github/workflows/batch-merge.yml`) needs nothing beyond this setup: it runs in the same Environment `agent`, mints the same app token, and merges only an `Issue batch` pull request of the app that passes the guards of the `merge` row above, so with the relay off (no app) it has nothing to merge. It runs when CI completes, when a pull request is marked ready for review, every hour, and by hand (Actions, Batch merge, Run workflow, on `main`); each run's summary lists every batch pull request it looked at and why it skipped it. To hold a merge, convert the pull request to draft.

To go back to the owner connector, empty the `login` in `.github/agent-identity.json` (or remove the file).

Rotate the key by generating a new one on the app page, replacing the environment secret, and deleting the old key there. If the key leaks, delete it on the app page at once; tokens expire within the hour.

The relay mints the token with `scripts/agent-token.mjs` (RS256 JWT, installation token scoped to this repository, one hour). The script also accepts the same PEM as base64 in `AGENT_APP_PRIVATE_KEY_B64`; if both variables are set they must hold the same key.
