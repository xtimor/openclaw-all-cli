## How it runs

OpenClaw selects the `cursor-cli` backend from the model ref `cursor-cli/<model>`. The plugin starts `cursor-agent acp` and talks to it over the Agent Client Protocol (ACP). One process serves one conversation. The plugin keeps it warm between turns (closed after 15 idle minutes) whenever OpenClaw allows reuse; see the P4 row. OpenClaw owns the session binding: it stores the Cursor session ID the plugin reports, and the next turn resumes it with ACP `session/load` when OpenClaw says to.

Each agent gets its own Cursor home, `<agentDir>/openclaw-all-cli/cursor-cli/` (`agentDir` is OpenClaw's per-agent directory). The plugin points `CURSOR_CONFIG_DIR` at it and `CURSOR_DATA_DIR` at its `data/` folder, so agents share no Cursor config or chat store. The Cursor login stays shared (the Keychain on macOS, `~/.config/cursor/auth.json` on Linux; the per-agent config directory still sees it, checked on Linux). The plugin writes nothing into the agent's working directory. If OpenClaw gives no agent directory, the turn fails with `OpenClaw gave no agent directory`; the plugin never falls back to a shared home.

The home holds one file the plugin writes, `cli-config.json`, with the same static permissions for every agent:

| Rule | Entries |
| --- | --- |
| Deny | `Shell(*)`, `Write(**)`, `WebFetch(*)` |
| Allow | `Read(**)`, `Mcp(openclaw:*)` |

The home directory is created with mode 0700 and the file with mode 0600 (an existing stricter file mode is kept). If `cli-config.json` exists but cannot be read, the turn fails and names the file instead of replacing it. The plugin writes the file once through an atomic rename and leaves it alone while it already holds these rules. Other keys Cursor stores there are kept, and edits to the `permissions` key are overwritten on the next turn. No per-turn policy goes into a file. Native read, grep, and glob stay available.

A turn runs in Cursor's `agent` mode only when OpenClaw's `exec` is really offered to the model in that turn: the plugin reads the host's tool list for the turn (after all of OpenClaw's tool policy) and looks for `exec`. Otherwise (a side question, exec host `node`, `tools.deny` or `tools.allow` leaving `exec` out, a rooted run, a tool list that cannot be read) it runs in `ask` mode, which has no edit tool. In `agent` mode the denied tools are blocked without Cursor asking: the native shell, write, edit, and delete (checked live, cursor-agent 2026.10.16, with this exact file). `WebFetch(*)` has no effect: a native web fetch asks OpenClaw (`web_fetch`) in either mode, and OpenClaw's tool policy decides. The model's shell is OpenClaw's own `exec`, see [Shell commands](#shell-commands-openclaw-exec).

## Sessions, resume, and side questions

OpenClaw owns which Cursor chat belongs to which OpenClaw chat. The plugin keeps no session map: it only receives `sessionId` and `useResume` for a turn and reports the Cursor session ID it ends up with, on every turn.

| Situation | What happens |
| --- | --- |
| Follow-up turn, warm process | The same `cursor-agent acp` process answers; only the new prompt is sent. Measured here (see Warm process and latency), the first text of a plain follow-up takes about 2 s in the plugin instead of about 5.5 s |
| Follow-up after a Gateway restart (or any turn OpenClaw restarts the process for: a changed system prompt, tool list, skills, model, working directory, or auth profile) | A new process loads the chat with ACP `session/load`; Cursor keeps the context, and only the new prompt is sent |
| `/reset` | OpenClaw passes no resume ID; the plugin starts a new Cursor session and reports its ID |
| Another agent's chat, or a chat deleted from the agent's home | `session/load` fails; the turn fails with `session_expired` and the text `CLI session not found: ...`. The plugin never starts a fresh chat behind it. The backend sets `freshSessionRecovery: "invalidated-only"`, so OpenClaw may retry once with a fresh Cursor chat and its own reseeded history, and only for an error like this one and only when it has history to reseed (needs a Cursor API-key profile, see [Chat continuity across a model switch](#chat-continuity-across-a-model-switch)). OpenClaw 2026.10.3 clears a failed chat binding only for `claude-cli`, and its fresh retry cannot run (see Chat continuity across a model switch), so every later turn fails the same way until you run `/reset` |
| Cursor answers `session/load` with another session ID | That ID is reported and used for the next turn |
| Cursor cannot load sessions at all | The turn fails with `capability_mismatch` |

A warm process serves the next turn only when model, mode, working directory, agent home, auth profile, thinking level, and Cursor session ID all match the turn (AD-13); otherwise it is closed and a new one resumes the chat. At most one process holds a chat: if a second process is about to load a chat an idle one holds, the idle one is closed first, and if that one is in the middle of a turn the new turn fails with a retryable error. A live probe (2026-10-18, cursor-agent 2026.10.16) showed why: Cursor lets two processes load one chat without an error, but each keeps its own view, a turn in one is invisible to the other, and the stored chat ends up with only one process's turns.

A side question (OpenClaw's `/btw`, `executionMode: "side-question"`) opens a throwaway Cursor session in `ask` mode, with no MCP server (so no OpenClaw tools), no resume, and every permission request rejected without asking OpenClaw. It reports no session ID, so the chat's binding is untouched, and its process closes after the answer. The backend sets `sideQuestionToolMode: "disabled"`. Cursor cannot switch off its native `read`, `grep`, and `glob` per run (see Known limits), so a side question may still read files, but it cannot run a shell, write, or call an OpenClaw tool. Cursor keeps the throwaway session in the agent's `acp-sessions` folder; once the side question's process has exited (and its process group is gone), the plugin removes that one directory, by its session ID. An agent chat's directory is never removed. A new chat Cursor refuses after `session/new` (an unknown model, a missing mode) keeps its directory, because the plugin never learns its ID.

## Warm process and latency

Starting `cursor-agent acp` and loading a chat costs about 3 s every time (measured on one machine, cursor-agent 2026.10.22: 0.6 s to `initialize`, 2.2 to 2.7 s for `session/new` or `session/load`, with or without Cursor's cached state, whatever the working directory). A turn that finds a warm process skips it. Plain turn, `cursor-cli/auto`, one-word answer, times from the call:

| Measurement | Process started for the turn | Warm process |
| --- | --- | --- |
| Plugin alone, first text | 5.4 to 6.5 s | 1.8 to 2.1 s |
| Through a Gateway, first assistant text of a follow-up | 9.2 to 9.4 s (before the fix: OpenClaw restarted the process every turn) | 5.0 to 7.6 s |

OpenClaw decides whether a turn may reach the warm process: it compares a fingerprint of the run (command and arguments, model, working directory, auth profile, system prompt, tool list, skills, environment) with the one of the live process. The plugin declares `bundleMcpMode: "claude-config-file"`, which keeps the per-turn MCP config path out of that fingerprint (see [OpenClaw tools](#openclaw-tools)). What still restarts the process, and resumes the chat with `session/load`, is a change in anything the fingerprint holds: a new system prompt or tool list, a model switch, another working directory or auth profile, or a Gateway restart. One change is easy to meet: a turn that starts in the first seconds after the Gateway starts gets a shorter tool list than the next one (see Known limits). The first text is as early as the model sends it; the plugin passes each delta on as it arrives and reads the turn's usage only after the text. Tool calls, and models that think for a long time, add their own time.

### First reply of a new chat

The first reply of a new session is slower than later ones ([#38](https://github.com/xtimor/openclaw-all-cli/issues/38)). Measured 2026-10-26 (cursor-agent 2026.10.22, OpenClaw 2026.10.3, `cursor-cli/auto`, a Gateway whose model catalog had loaded, the main agent with its first-run `BOOTSTRAP.md`, `openclaw agent` with a new session ID and "Reply with the single word OK."): first assistant text 22 to 29 s on the first turn (5 sessions), 5.5 to 9.3 s on follow-ups. Where the time goes (the plugin's parts from two traced sessions):

| Part | First turn | Follow-up (warm process) |
| --- | --- | --- |
| OpenClaw, from the `openclaw agent` call until it hands the turn to the plugin | 3.0 to 5.3 s | 2.7 to 3.0 s |
| Process start (spawn to the answer of `initialize`) | 0.6 to 1.0 s | none |
| `session/new` | 3.2 to 3.3 s | none |
| From the prompt to the model's first output; on the first turn the prompt carries the bootstrap, OpenClaw's system prompt and the continuity note (42 KB; about 24k input tokens with Cursor's own prompt) | 2.4 to 3.0 s | 2.2 to 2.5 s |
| The model thinking before its first text | 9.3 to 12.2 s (800 to 1000 output tokens) | 2.6 to 3.8 s |

The biggest part is the model's own thinking over the agent's instructions on the first turn. The prompt's size alone costs little: a 36k-character text that holds no instructions (about 16k tokens) delayed the first text by about 1 s against a short prompt, in a bare ACP probe. An agent without `BOOTSTRAP.md` (a workspace already set up) was not measured.

**No warm start before the first turn.** The plugin does not pre-start `cursor-agent` or pre-load a chat per agent. What was checked:

- **Fork or copy of a prepared chat.** cursor-agent 2026.10.22 has no ACP fork, resume, or close (`session/fork`, `session/resume`, `session/close` answer `Method not found`; `initialize` reports only `sessionCapabilities.list`). Copying a chat's folder under a new ID loads and keeps the chat's content, and the copy's turns stay out of the original locally, but Cursor's server books the copy's turns under the original chat's ID: the plugin's usage lookup (by chat ID) would miss or mix them, and whether Cursor keeps other server state per chat ID is unknown, so two sessions, or two agents, could share it. The folder format is Cursor's private one.
- **Bootstrap tokens and a stale bootstrap.** A prepared chat costs a model turn of about 24k input tokens before anyone writes, used or not, and it would hold a fake first turn. Its system prompt dates from when it was prepared (date, runtime fields, workspace files), so a changed prompt is sent again anyway.
- **A spare process per agent.** It would save at most process start and `session/new` (about 4 s of 22 to 29 s). It costs memory while idle: about 170 MB after `initialize`, about 870 MB after `session/new` (sum over the process group: the agent, `worker-server`, a TypeScript language server; shared pages counted twice). `session/new` already binds the chat's working directory and OpenClaw's tools (the MCP server), which exist only once OpenClaw starts the turn, and Cursor drops a server it could not reach for the life of the process. OpenClaw also owns which process serves a session (its live-session registry, checked by a fingerprint of the run), and a new session never has a live process to reuse. A spare process would need a change of the plugin's architecture; it is not built.
- **Resume.** Loading a chat (`session/load`) costs as much as a new one (2.6 to 3.0 s), so a resumed prepared chat saves nothing.

### Per-turn timing line

Every turn writes one line to OpenClaw's debug log ([#44](https://github.com/xtimor/openclaw-all-cli/issues/44)), so the next measurement is exact and silence can be told from thinking. The plugin logger's debug channel is off at OpenClaw's default level: start the Gateway (or the `openclaw agent --local` run) with `OPENCLAW_LOG_LEVEL=debug`, then search the log for `turn timings`. Checked on OpenClaw 2026.10.3: the line shows at `debug` under `[plugins]` and not at `info`.

```text
turn timings (cursor): model=grok-4.7 process=new outcome=ok spawn=9ms initialize=660ms new_session=3639ms set_mode=5ms set_model=877ms prompt_sent=5712ms first_thought=1800ms first_text=3218ms end=3481ms
```

| Field | Meaning |
| --- | --- |
| `model` | The model name OpenClaw asked for. |
| `process` | `new` (this turn started `cursor-agent`) or `reused` (a warm process; follow-ups). |
| `outcome` | `ok` (the turn ended with a result), `error` (with `code=<error code>`, also for a chat that could not start or load), or `aborted` (the host stopped the turn). |
| `spawn` | From the start call until the process exists. |
| `initialize` | From the `initialize` request until its answer. The process boots inside it, so this is the process start. |
| `login` | `authenticate`, only without `CURSOR_API_KEY`. |
| `new_session` or `load_session` | Whichever ran: a new chat, or the resume of an existing one. |
| `set_mode` | Only when the session had to be switched to the plugin's mode. |
| `set_model` | Only when the model had to be switched (Auto needs none on a fresh session). |
| `prompt_sent` | Milliseconds from the start of the turn (the wait for a turn slot, the version check, the MCP proxy, and the open all come first) until the prompt was sent. What the phases above do not add up to is that other work. |
| `first_thought`, `first_text`, `end` | Milliseconds after the prompt was sent: the first reasoning chunk, the first reply text, the closing result. `first_thought` is absent when the model sent no reasoning. `end` is the result reaching the plugin, before the usage lookup. |

The open phases are durations; the last four fields are positions on the turn's clock. A phase that did not happen has no field, never `0`; a phase that ran counts at least 1 ms. A turn that fails still writes its line with the phases it reached. The line holds no prompt text, key, or path. The marks come from the plugin's own clock: `first_text` is when the plugin sees the chunk, which can be later than Cursor sent it by a few milliseconds.

**Where the wait goes, live.** Measured 2026-10-28 (cursor-agent 2026.10.22, `CURSOR_API_KEY`, the plugin's backend driving the real `cursor-agent` directly with a new agent home per turn and the prompt "Reply with the single word OK."; three turns per model, ranges). This run has no OpenClaw around it, so it lacks OpenClaw's own 3 to 5 s before the plugin and the 42 KB system prompt, and the model thinks far less than in the table above:

| Field | `grok-4.7` | `auto` |
| --- | --- | --- |
| `spawn` | 9 to 23 ms | 9 to 10 ms |
| `initialize` | 612 to 836 ms | 635 to 760 ms |
| `new_session` | 3344 to 4446 ms | 3091 to 3611 ms |
| `set_mode` | 5 to 22 ms | 4 to 9 ms |
| `set_model` | 846 to 1412 ms | none (Auto is the session's model) |
| `prompt_sent` | 5712 to 6701 ms | 4451 to 4842 ms |
| `first_thought` | 1675 to 1860 ms | 1605 to 1867 ms |
| `first_text` | 2897 to 3448 ms | 1609 to 1913 ms |
| `end` | 3116 to 3704 ms | 1769 to 2119 ms |

Before the prompt, `new_session` is the largest part (3.1 to 4.4 s), then the model switch on `grok-4.7` (0.85 to 1.4 s) and the process start (about 0.7 s). The 0.5 to 1.2 s that `prompt_sent` has beyond those phases is the plugin's other work before the open (the first-process version check, the MCP proxy). Model selection stays after `session/new`/`session/load` on purpose: the exact model ID (brackets included) is read from the list that call returns, so the switch cannot be sent beside it.

## Chat continuity across a model switch

When you switch an OpenClaw chat from an API model to `cursor-cli`, Cursor starts a fresh chat and does not see the earlier turns: OpenClaw 2026.10.3 sends only the new prompt (log: `historyPrompt=none`, `cli session history refused across auth boundary: reason=auth-unknown`). It refuses on purpose, because it copies history only into a CLI chat written by the same credential from the start. A Cursor API-key profile does not change this for a switch.

So the plugin adds a short note, once, in front of the first prompt of every fresh Cursor chat that has OpenClaw's tools (the MCP proxy). It says that the chat is part of an OpenClaw conversation and that turns by other models are not in Cursor's context, and it tells the model to read them with OpenClaw's `sessions_history` tool (`sessionKey: "current"`) when the user refers to something it cannot see. The note is about 380 characters (about 90 tokens), it stays in the Cursor chat for later turns, and it is not written to OpenClaw's transcript. It is not added to a resumed turn, a warm follow-up, a side question, or when MCP is off.

- **The tool is OpenClaw's, under OpenClaw's policy.** If `tools.deny` hides `sessions_history`, or session visibility limits it, the model cannot read the history and answers without it. The note says "if that tool is available".
- **It needs a Gateway.** `sessions_history` runs through the Gateway, so it fails in `openclaw agent --local`. Run the chat through a Gateway.
- **A lost chat with a profile.** With a `cursor-cli` `api_key` profile (see [setup](../setup.md)), the backend sets `reseedFromRawTranscriptWhenUncompacted` (as `claude-cli` does). OpenClaw then builds its history prompt (`<conversation_history>`, capped at 12 288 characters) for a `cursor-cli`-only chat, also on resumed turns and when it starts a fresh chat after an MCP or working-directory change (a system-prompt change no longer starts one: the chat is kept, see System prompt and skills); the note is added to that prompt too. Live probe (OpenClaw 2026.10.3): for a lost chat the history prompt is built (`historyPrompt=present`) but the host's fresh retry cannot run, so the turn fails until `/reset`, with or without a profile. The host mints one MCP loopback grant per run. The fresh retry reuses the same prepared backend, so it gets no new grant. In the first attempt the plugin's `live.register` stores the run's own grant token; `session/load` fails, the plugin closes its handle, and `live.remove` revokes that token; the retry's register/activate then throws `CLI MCP client grant is no longer valid`. Skipping the close does not help (the host closes the record itself on a fresh retry). Through a Gateway the retry is blocked earlier: the host's session-entry copy has a stale `activeWriterRunId`, so it cannot clear the failed binding. So a lost chat is host-blocked in both paths on OpenClaw 2026.10.3. The only plugin-side fix would be a probe that the native chat exists before `live.register` (fragile, changes resume behavior); deferred.
- **Back to Cursor.** After cursor, then an API model, then cursor again, the chat resumes and the first prompt's note is still in Cursor's context. In the live probe the model called `sessions_history` and gave the fact from the API turn; this is not guaranteed.
- **No fallback prelude (gap).** When a turn on `cursor-cli` is followed by an API model, OpenClaw 2026.10.3 builds its fallback prelude only for `claude-cli`. The API model still gets the user and assistant text of the cursor turns from OpenClaw's transcript (live test); only Cursor's internal tool detail is lost.

Live test: `test/live/history-continuity.live.test.ts`.

## OpenClaw tools

OpenClaw's tools (`sessions_list`, `memory_search`, `web_fetch`, and the rest) reach Cursor as the MCP server `openclaw`. The backend sets `bundleMcp` with `bundleMcpMode: "claude-config-file"` (the mode `claude-cli` uses), so for every turn OpenClaw writes an MCP config file with its own loopback URL, a fresh token, and a capture key, and names it in a `--mcp-config <file>` launch flag. The plugin removes that flag, `--strict-mcp-config`, and `--disallowedTools` from the launch, since `cursor-agent` knows none of them. The URL and token are not Cursor's to hold, so the plugin never gives them to Cursor. Instead it runs one local HTTP proxy per live session, on `127.0.0.1` with a random port and its own random Bearer token, and hands Cursor only that proxy through ACP `mcpServers` (`session/new` and `session/load`). When a process opens, the plugin reads `mcpServers.openclaw` (`url` or `httpUrl`, and `headers`) from the config file and points the proxy at it; the proxy forwards method, path, body, and the response stream unchanged, with `Authorization` and `x-openclaw-cli-capture-key` headers from that file. A warm process keeps that target for its later turns: OpenClaw moves each later run's grant onto the process's own token and capture key, so the later file's credentials are not the ones OpenClaw accepts for this process. A later turn still reads its own file, and runs without OpenClaw tools if the file is unusable. Between turns, after an abort, and after the proxy's session closes, the proxy rejects every call.

| Situation | What happens |
| --- | --- |
| Call outside a turn | HTTP 503 with a JSON-RPC error; nothing is forwarded |
| Missing or wrong client token | HTTP 401; nothing is forwarded. The token is checked before the path, so a wrong token gets 401 even for a path outside `/mcp` |
| Path outside `/mcp` | HTTP 404; nothing is forwarded |
| Proxy failure while handling a call | HTTP 500 with a JSON-RPC error |
| The proxy cannot start | The turn fails with a retryable error; Cursor is not started |
| The live session was closed while Cursor was starting | The new Cursor process is stopped and the turn fails with a retryable error (`The live session was closed while the CLI was starting`) |
| OpenClaw's endpoint unreachable | HTTP 502 to Cursor; the turn continues |
| No `--mcp-config` flag, no config file, or no `mcpServers.openclaw` in it | The turn runs without OpenClaw tools and the plugin logs a warning; the chat does not fail. Cursor drops the `openclaw` server for the life of that process, so a process whose first turn had no config is closed when that turn ends and the next turn starts a new one. A warm process whose later turn has no usable config keeps running; only that turn has no tools |
| Config URL is not a loopback `http` URL | Treated as no config, so the proxy never sends OpenClaw's token anywhere else |

Cursor connects to its MCP servers while it opens the session, before the first prompt, so the plugin registers the session with OpenClaw and points the proxy at the turn's endpoint before it starts `cursor-agent`. The plugin writes no MCP configuration into the workspace or any file you own.

## System prompt and skills

Cursor has no system-prompt channel on ACP (`session/new` takes only the working directory and MCP servers), so the plugin sends OpenClaw's system prompt (workspace files such as `AGENTS.md` and `SOUL.md`, the tool list, safety rules, runtime facts, and the skills catalog) as a block at the start of the prompt. The block has a header that says it holds OpenClaw's system instructions, then the text between `<openclaw_system_prompt>` tags. It goes in Cursor's chat only, never into OpenClaw's transcript, and the plugin writes no instruction or skill file into the workspace or your home.

- **When it is sent.** On the first prompt of a chat, and again when the prompt differs from what that chat last received (an edited workspace file, a skill added or removed, a tool list change, a model identity change). The new block says it replaces earlier OpenClaw instructions. An unchanged prompt is not resent: it would add thousands of tokens to Cursor's chat on every turn.
- **What does not count as a change.** The change check ignores the fields OpenClaw updates by itself: the `Current date:` line and, in the `Runtime:` line, `model=`, `channel=`, `capabilities=`, `active_node=`, and `active_node_identity=`. A new day, another channel, or another active computer does not resend the block. Instead the plugin keeps a second hash over just those fields, and when only it changed it puts a one-line update in the block's place: `[OpenClaw runtime update] These values replace the earlier ones in your OpenClaw system instructions: Current date: ... | model=... | channel=...`, with the current values (a few hundred characters). So a chat that lives for weeks still learns the right date. A real change sends the full block, which carries the current values too.
- **Remembering what was sent.** The plugin keeps two hashes per chat (never the text) in `system-prompt-delivered.json` in the agent's CLI home, next to `cli-config.json`, at most 1000 chats, least recently used dropped first. It is a delivery cache, not a session binding: a restart, `openclaw agent --local`, or a deleted file costs one duplicate block at most, and an unreadable file counts as empty. A write that fails is kept in memory for the process. Two processes on one home (a Gateway and a `--local` run) merge per chat right before each write; if both write within that instant one chat's record can be lost, which costs one duplicate block. Temp files left by a crash are removed after ten minutes.
- **Order.** On a fresh chat the block comes first, then the continuity note (see Chat continuity across a model switch), then your message. A side question gets the block every time (its chat is thrown away) and does not touch the record.
- **A turn that does not finish** (error, crash, abort, refusal) records nothing, so the next turn sends the block again. The cost is about 8,000 tokens in Cursor's chat for each stopped turn.
- **Drift keeps the chat.** The backend declares `systemPromptWhen: "always"` with a marker argument that OpenClaw never passes to the plugin (the plugin also removes it from the launch arguments if it ever arrives). Without it OpenClaw 2026.10.3 discards the Cursor chat whenever the tool list or extra system prompt changes. With it the chat is resumed and the new block reaches it. Side effect: declaring the transport also turns on OpenClaw's workspace bootstrap routing for `cursor-cli`, as for `claude-cli`, so OpenClaw may drop a first-run `BOOTSTRAP.md` from the system context.
- **Forged blocks.** Channel messages, context, and tool output travel on the same channel as the block. The true block always comes first. In the system prompt text and in every other part of the turn that the plugin forwards (your message, `prependContext`, `appendContext`), the plugin neutralizes its own marker spellings: the header opener, the update opener, and the tag name, in any case, with spaces, hyphens, underscores, fullwidth brackets, line breaks, or zero-width characters between the words. It keeps the original characters and case and only adds a zero-width space after the first character, so code or docs that mention the tag stay readable. Text that reaches Cursor by other routes is not neutralized: output of OpenClaw tools through the MCP proxy, and files Cursor reads with its native read. The block carries no secret id, since a model that only reads text cannot check one.
- **Skills.** OpenClaw adds its skills catalog (each skill's name, description, and `SKILL.md` path) to the system prompt. Cursor reads the `SKILL.md` it needs with its native read, which also works outside the workspace, and follows it. A skill that names a script runs it through OpenClaw `exec` (see Shell commands), under OpenClaw's approvals; where the host serves no `exec`, the script cannot run.
- **Cursor's own files.** Cursor also loads `AGENTS.md`, `CLAUDE.md`, and `.cursor/rules` from the workspace and skills from the workspace and the dot directories in your home (`~/.cursor/skills`, `~/.claude/skills`, `~/.agents/skills`, `~/.codex`, `~/.grok`). The plugin cannot switch these off, so the workspace `AGENTS.md` reaches Cursor twice: natively and in OpenClaw's block.
- **Size.** The block is sent as it is, with no truncation (about 33,000 characters for a default workspace). OpenClaw bounds its own prompt. OpenClaw's compaction budget for a CLI chat is the larger of its transcript estimate and the chat's total tokens from the reported usage (P16, needs `CURSOR_API_KEY`), and that total includes every copy of the block in Cursor's chat. So with an API key a long chat reaches the budget sooner, and the compaction needs an API model or a Cursor API-key profile (see Known limits).

Live test: `test/live/skills-system-prompt.live.test.ts`. No setup change is needed.

## Images

An image you attach to a `cursor-cli` turn reaches Cursor as pixels, not as a path. OpenClaw 2026.10.3 writes the image to its private cache (`<OpenClaw temp>/openclaw-cli-images`, mode 0700, swept after 7 days) and, because the backend declares no `imageArg`, appends the file paths at the end of the prompt. The plugin takes that path block off the text, reads the files, and sends them as ACP `image` blocks after the text block. Cursor never sees the cache path, so its native read cannot open it.

- **What counts as the host's block.** The trailing lines of the prompt, after an empty line (or the whole prompt), where every line is an absolute, normalized path `<temp>/openclaw[-<uid>]/openclaw-cli-images/<64 hex>.<ext>`. The directory under the temp dir must be `openclaw` or `openclaw-<your uid>` exactly, directly under `/tmp` or the system temp dir. A block of more than 18 lines is not the host's. Every file must also have been written within the 15 minutes before the turn began. The host writes the files when it prepares the turn, before it waits in its own per-session queue, and that wait (behind a long run on the same session, a heartbeat or cron run) is the only legitimate delay, so the window is generous. A path that a user or a channel typed for an older cache file, or for a file that is gone or that another user owns, is left as text and no file is read. An old file that the Gateway's user owns in the host's private directory is most likely the host's own block after an even longer wait: the paths stay in the text, one `[OpenClaw] ... too old to be read` note asks the model to tell you, and the plugin logs a warning without the path. If any line fails, the prompt goes through unchanged. A cache path in the middle of your text is left alone.
- **What is sent.** Each file must be a regular file with a single link (no symlink), owned by the user running the Gateway, in a directory that user owns and that group and others cannot write to, and PNG, JPEG, GIF, WebP, or BMP **by its first bytes**, never by its extension (a `.png` that holds JPEG goes as `image/jpeg`). The file is opened without following links and checked again on the open descriptor; a file the host rewrote in between is tried once more. At most 10 MiB per image, 10 images, and 20 MiB per turn. An image that does not fit the rest of the 20 MiB is skipped and smaller ones after it still go. HEIC, AVIF, SVG, TIFF, empty files, and unknown bytes are not sent. OpenClaw itself already caps an image at about 6 MiB before it writes the cache file, so the plugin's 10 MiB cap rarely applies; the 10 images and 20 MiB totals are the plugin's own.
- **Nothing is dropped silently.** An image that cannot be sent is removed from the text and replaced by a one-line note at the end of the prompt, for example `[OpenClaw] An attached image was not passed to the model: unsupported type. Tell the user it could not be used.` (also `too large`, `empty file`, `no longer available`, `could not be read`, `over the total size limit`, or a count of images left out for too many images). The note asks the model to tell you, since you otherwise never learn it. The plugin logs a warning with the reason only: never the path, the bytes, or base64.
- **Nothing is written.** The plugin creates, copies, changes, and deletes no image file, in the workspace, a home, or the temp dir. The cache belongs to OpenClaw, which sweeps it. The images go to Cursor's server as part of the chat, like any prompt text.
- **Later turns.** Cursor keeps an image in its chat, so a later turn of the same chat (also after `session/load`) can ask about it and the plugin resends nothing. After a fresh chat (a lost chat, `/reset`, or compaction, see Compaction) the earlier images are gone from Cursor's side; attach the image again.
- **Local images named in your text.** OpenClaw also attaches local images your message names (inside the agent's allowed folders) in the same way, so they arrive as image blocks too.
- **Side questions** get their images like any other turn.
- **Models.** The catalog rows declare `text` and `image` input, so OpenClaw routes images to Cursor models instead of treating them as files.
- **Requirement.** `cursor-agent` must report `promptCapabilities.image` at open (see Capability check). A build that does not fails every turn with `capability_mismatch`, text-only turns too, because the check runs at open before the prompt is known. That is by design: update the CLI.
- **Windows.** The owner check needs a process uid, which Windows has none of. There the plugin leaves the prompt as it is (the host's paths stay in the text, no image block is sent) and logs one warning per image turn. The catalog still lists image input, so images are not delivered as pixels on Windows. macOS and Linux are supported.

Live test: `test/live/images-compaction.live.test.ts` (real Cursor reads a random word from a PNG with no native read and recalls it in a later turn; a fake agent shows the blocks).

## Compaction

Cursor's ACP mode has no compaction control. `available_commands_update` lists none, `/summarize` and `/compress` sent over ACP are plain model text that leave the chat store unchanged, and the TUI's `/summarize` uses a conversation action the ACP agent never sends. Cursor may summarize a long chat on its own server, but nothing shows it or can trigger it. So the backend declares neither `ownsNativeCompaction` nor `manualCompaction`, and OpenClaw compacts its own transcript as it does for any CLI backend.

- **`/compact`.** It (`sessions.compact`) summarizes the OpenClaw transcript with an API model: `agents.defaults.compaction.model`, else the agent's own model. It then drops the Cursor chat binding. The next turn starts a fresh Cursor chat with the system block and the continuity note, and the model reads the compacted conversation through `sessions_history`. Cursor's own chat (and any image in it) is not carried over. Live-tested with a mock API compaction model.
- **Budget compaction (unverified).** OpenClaw also compacts before a turn when the chat crosses its `cli_budget`. It is expected to do the same as `/compact` for this backend, but no live test covers it.
- **What it needs.** An API model for the summary: `agents.defaults.compaction.model`, or an agent model with an API login. Whether a Cursor API-key profile counts as that login is unverified; set `agents.defaults.compaction.model` to be sure (see [Setup](../setup.md#3-configure)).
- **Without an API model (partly unverified).** `/compact` answered the host's reason (for example `No route-compatible authentication source is configured for openai`) in the probe. That the Cursor chat then stays as it is, and that a turn that crosses the budget then fails, are expected but not tested.
- **Where to send `/compact`.** It is a chat command, so it cannot go through `openclaw agent --message`. Use a chat channel or `openclaw sessions compact <key>` against a running Gateway.

Live test: `test/live/images-compaction.live.test.ts` (row e: a mock API compaction model, `sessions compact` reports `compacted: true`, the next turn opens one new Cursor chat and still knows the earlier fact).

## Streaming and tool progress

Cursor's replies reach OpenClaw while the turn runs, not when it ends: every `agent_message_chunk` becomes a text delta and every `agent_thought_chunk` a thinking delta, in order, and the closing record carries the full reply, which is exactly the concatenation of the text deltas. Nothing waits for the end of the turn. Live run (real `cursor-agent`, 2026.10.16): 159 text and 4 thinking deltas, the first one 9.6 s before the closing record.

The closing record's text is not a second block for the host (checked in OpenClaw 2026.10.3's CLI runner and with a Gateway, 2026-10-22): it only sets the turn's final text, which falls back to the streamed text when empty. The "completed block" path serves only the built-in Claude records. A webchat turn is the streamed deltas, then one `chat` `final` with the whole reply; the transcript holds one assistant row. The host also emits its own `assistant` snapshot with the final text after every CLI run.

Cursor's tool activity (`tool_call` and `tool_call_update`) shows as tool progress in OpenClaw. Rules:

- **Once per call.** However many updates Cursor sends for one call ID, OpenClaw gets one start and at most one result (at `completed` or `failed`; a failed call is marked as an error). An update for a call the plugin has not seen counts as its start.
- **Names.** Cursor announces a call with a generic title and, for search and MCP calls, no input; the next update, a few milliseconds later, has both. The plugin waits for that update, then shows the call under OpenClaw's tool names: `read`, `grep`, `glob`, `exec`, `edit`, `write`, `delete`, `web_fetch`, `web_search`, or `mcp__<server>__<tool>`. A call to OpenClaw's own tools through the MCP proxy shows as `mcp__openclaw__<tool>`, as in `claude-cli`; OpenClaw displays that without the prefix. The host adds no display of its own for a proxied call (checked live: its tool summary counts one entry), so the plugin does not hide it.
- **Nothing left pending.** A call still open when the turn ends, fails, or is cancelled gets a closing result marked as an aborted error.
- **Display only.** The events change no permission and no tool policy. Approvals still go through the permission requests described below.
- **Results are shortened.** A result longer than 8 000 characters is cut, because the events only feed the display.
- **Retries.** An error after any tool call started in the turn is not retryable, because the call may already have run. A process that dies before any tool call is retryable. OpenClaw's JSONL contract carries only the error text, so the host never sees this flag; it is in the plugin's own event for logs and tests.

## Errors

Cursor reports a failed turn (network, sign-in, rate limit, plan) as its last reply chunk, then ends the turn normally (`end_turn`). Read as it comes, that is a reply that happens to say "Error". The plugin recognises these chunks and turns them into an error turn, so OpenClaw's failover, retries, and transcript see an error and no assistant message is written. Cursor's text is kept in the error message. Live check (cursor-agent 2026.10.19, `test/live/errors.live.test.ts`): a proxy that refused the model host after the session started gave `Cursor internal server error: Error: RetriableError: [internal] HTTPS proxy CONNECT failed: 403 Forbidden`, a failed `openclaw agent` run, and no reply text.

A chunk counts only when it is the last thing in the turn. If any text, thinking, or tool call follows, it was ordinary text and stays in the reply in order. A cancelled turn drops it.

| Cursor says | OpenClaw error class |
| --- | --- |
| `Error: [unauthenticated]` or `[permission_denied]`, `Please sign in to continue` | `auth` |
| `Error: [resource_exhausted]`, `Upgrade your plan to continue` | `rate_limit` |
| `Add a payment method to continue` | `billing` |
| `Check your settings to continue` | `auth_permanent` |
| `Error: [unavailable]` | `overloaded` |
| `Error: [deadline_exceeded]` | `timeout` |
| `Error: [invalid_argument]` | `format` |
| `Error: <Name>: [internal]`, `[unknown]`, any other code (`[failed_precondition]` too), or a name without a code | `server_error` |

The error is retryable only when Cursor names it `RetriableError` and no tool call started in the turn. The plugin does not retry by itself. The host picks its own failover reason from the message text, so each message names the failure in words the host reads (for example "rate limit reached (usage limit)", "payment required") before Cursor's text. A Cursor server error carries "internal server error", which the host files as `timeout` (its class for transient server errors), so it gets its retry and cooldown handling. A session that fails to start gets Cursor's reason too (`Failed to initialize session services`).

## Permissions and tool availability

OpenClaw owns approval authority; the plugin only asks. The static `cli-config.json` is the first line of defence: it denies shell, writes, edits, and deletes, so Cursor blocks them without asking. A permission request still arises for what the file leaves open (for example a web fetch or search, or another MCP server). The plugin names the request in OpenClaw's terms (`exec`, `write`, `edit`, `delete`, `web_fetch`, `web_search`, `read`, `grep`, `glob`, or `mcp__<server>__<tool>`), asks the host (`requestToolPermission`), and answers Cursor from the result:

| Situation | Answer to Cursor |
| --- | --- |
| The host allows | `allow_once` |
| The host denies | reject. A denied shell request makes the model use OpenClaw `exec` instead |
| Asking the host fails, or the answer is malformed | reject (fail closed); the failure is logged and the turn continues |
| The host allows but changes the input | reject: Cursor can run only what the host saw |
| Cursor offers no option of the decided kind | `cancelled` |
| The turn is aborted while the host waits for a human | `cancelled` at once; the turn ends cleanly and the process closes as soon as the turn ends (the 5-second abort grace only bounds a CLI that ignores the cancel) |
| A request arrives after the turn ended, was aborted, or was superseded | `cancelled`; the host is never asked |
| A request the plugin cannot name (an unknown operation, a question prompt) during a turn | reject; the host is not asked (after the turn it is `cancelled`, like any late request) |
| The run's tool selection leaves the tool out | reject; the host is not asked |

The plugin starts no timer for approvals; OpenClaw's own timers apply. A run's tool selection (`toolAvailability`) comes from OpenClaw. The backend declares `nativeToolMode: "selectable"` with `execution-args` enforcement, as `claude-cli` does. Its `resolveExecutionArgs` returns OpenClaw's launch arguments unchanged for a selection that keeps native `read`, `grep`, and `glob` on, and nothing otherwise, which makes OpenClaw fail the run (Cursor cannot switch them off per turn and the plugin writes no per-turn policy file). OpenClaw 2026.10.3 asks for `native: []` for runs with a tool cap, tools disabled, or a system agent; such a run is refused before Cursor starts, with `cursor-cli keeps native read, grep, glob on in every turn...`. A run without a selection starts as usual. `tools.allow` and `tools.deny` filter the OpenClaw tool list on OpenClaw's side; the plugin translates nothing.

Native edits cannot ask in ACP: in agent mode Cursor never requests approval for them, and its `ask` and `plan` modes have no edit tool. So edits stay denied by `Write(**)` in the static file. A turn uses `agent` mode only when `exec` is in the host's tool list for the turn (the backend's `resolveExecutionArgs` marks a run where the host may serve it, and the plugin then reads the list), because in `ask` mode the model refuses any command that changes files even through OpenClaw `exec` (live: 2 of 3 tries refused). All other turns, side questions included, use `ask` as a second lock; the plugin refuses to open a session when `cursor-agent` lacks the mode it needs. The cost of `agent` mode: the model is more eager to act. A plain "remember this" turn made 6 tool calls (native read, glob, edit, and shell; the denied ones were blocked) and used about 105 000 tokens in one live probe. If a turn's tokens exceed OpenClaw's context budget, OpenClaw compacts the transcript after the turn, and that fails without an API model to summarize it (see Known limits).

## Shell commands (OpenClaw exec)

The model's shell is OpenClaw's own `exec` tool, with `process` for background commands. The backend declares `toolAvailabilityEnforcement: "execution-args"` and `hostOwnedTools: ["exec", "process"]`, the same mechanism `claude-cli` uses, so OpenClaw puts both tools on the MCP endpoint the plugin's proxy forwards to Cursor. The plugin runs, parses, and filters no command. What OpenClaw's exec does applies unchanged:

| Situation | What happens |
| --- | --- |
| Default policy | The command runs in the turn's workspace and its output goes to the model |
| `tools.exec.ask: always` | OpenClaw holds the command as a pending approval (`exec.approval.list`). It needs a client that can answer approvals (the Control UI, an app, or a chat channel with approvals); a headless `openclaw agent` run has none, and OpenClaw denies the command at once. Allow once runs it, deny does not |
| `tools.exec.security: deny`, or a denial | The command does not run and the model gets OpenClaw's reason. It cannot fall back to Cursor's shell: that stays denied |
| `timeout` parameter or `tools.exec.timeoutSec` exceeded | OpenClaw kills the command and reports the timeout to the model; the turn goes on |
| Very large output | OpenClaw's output cap truncates it; the turn completes |
| Non-zero exit | The exit code and output go to the model |
| Turn aborted while a command runs | The plugin closes the call, OpenClaw kills the command's processes (live: gone within 10 s), and the turn ends with the abort error |
| A foreground command runs past 55 s | The plugin stops the call (see below): the command is killed and the model gets a tool error |
| `tools.deny: [exec, process]`, or `tools.allow` without `exec` | `exec` is not offered, so the model has no shell, and the turn runs in `ask` mode (the plugin saw no `exec` in the tool list) |
| Sandboxed agent | OpenClaw runs the command in the sandbox, or refuses; the plugin does not choose |

### The 60-second call limit

Cursor's MCP client gives up on a tool call after 60 s (`MCP error -32001: Request timed out`), whatever keepalive frames the host sends, and it does not hang up the request. OpenClaw's `exec` kills a command only when the request closes, so a foreground command longer than that would keep running while the model saw a timeout and started it again. So the plugin's proxy gives every forwarded `tools/call` a deadline of 55 s. At the deadline it aborts the upstream request (OpenClaw then kills the command) and answers Cursor with a tool error that says the call ran too long, was stopped, and that long commands belong in the background (exec with `background` or `yieldMs`, polled with `process`). It does not read the tool name or arguments, and other requests have no deadline. A response that already carries its result is left alone. A batched request that contains a `tools/call` gets the same deadline and is answered as a batch: the tool error for each stopped call, and a JSON-RPC error for each other request in it. A backgrounded command returns early and is not affected.

OpenClaw's `exec` backgrounds a command by itself after `yieldMs` (10 s by default) and returns a session ID, so the deadline rarely fires with the defaults. It fires when the command stays in the foreground: `tools.deny` hides `process` (OpenClaw then runs `exec` synchronously and ignores `yieldMs` and `background`), or a call sets `yieldMs` beyond 55 s. With `process` hidden, anything over 55 s is stopped with no way to poll it. Keep `process` available, or keep commands short.

### Limits that come from Cursor or the host

- **No `exec` for some runs.** OpenClaw serves `exec` as a host tool only to a normal run whose exec host is not `node` and that is not rooted. A run with a tool cap, tools disabled, or a system agent (OpenClaw sends `native: []`) is refused before Cursor starts. A rooted run, and a run with exec host `node`, start but have no `exec`. `claude-cli` falls back to its native Bash there; `cursor-cli` has no native shell to fall back to. In these runs a native shell request from Cursor is protected by `Shell(*)` in the home's `cli-config.json` alone (OpenClaw answers "Use OpenClaw exec" only where it serves exec).
- **Commands can read the Gateway's environment.** A command run through `exec` inherits the Gateway's environment, so any variable there, `CURSOR_API_KEY` included, is readable by anything the model runs. The plugin does not strip it. The login and the key differ only in where they sit. The login avoids the Gateway's environment and the OpenClaw config file. A key given to the Cursor process through the plugin config stays out of `exec`'s environment, but is held by the config file and its rotated copies. Both end up in `~/.config/cursor/auth.json` on Linux (the login's tokens; the key too whenever `cursor-agent` runs with it), which a command running as the same user can read, as it can read the `cursor-agent` process's environment. That file is not the per-agent Cursor home. Against `exec`, exec approvals and a sandbox are the protection for both. See [Setup](../setup.md#the-api-key) for removing every copy. Keep exec approvals on (`tools.exec.ask`) for untrusted prompts. Declaring the key in the plugin manifest (`setup.providers[].envVars`) does not remove it from `exec`.
- **A command can write the Cursor home.** `exec` runs as the Gateway's user, so it can rewrite `cli-config.json` in the agent home. The plugin restores only the `permissions` key at the start of the next turn; anything else Cursor reads from that file stays as the command left it. Treat approving a command as trusting it with the agent home.
- **A sandboxed agent has two workspaces.** `exec` runs in the sandbox's working directory, but Cursor's native `read`, `grep`, and `glob` read the host workspace, and those reads leave the sandbox. A sandbox does not confine what the model can read.
- **A selection that includes native `exec`.** If a run's tool selection lists native `exec`, the backend accepts it, although Cursor can never run a native `exec` (`Shell(*)` is denied). This is over-restrictive, not a bypass: that run's model has no shell of its own beyond what the host serves.

## Provider list and sign-in methods

The `cursor-cli` provider is in OpenClaw's provider list (Control UI: Models, **Connect provider**, group **OAC / Cursor-CLI**) with two methods, declared in the manifest (`providerAuthChoices`, credential-only so the dialog lists them) and registered by the plugin (`registerProvider`, which carries only the methods; the catalog and the native login stay with the provider-catalog entry, `prepareSyntheticAuth` unchanged):

- **`login`, "Use the cursor-agent login".** No fields. It runs the adapter's login probe (`cursor-agent status`, with the plugin config's `command` and `env`, without the cleared env keys) and reports logged in, or fails with ``Cursor CLI is not logged in. Run `cursor-agent login` ...``. It leaves a `CURSOR_API_KEY` out of the probe, so it reports the login itself, and says so when a key is set too.
- **`api-key-env`, "Cursor CLI API key (CURSOR_API_KEY)".** Asks for a hidden key and returns a config patch that sets `plugins.entries.openclaw-all-cli.config.cursor-cli.env.CURSOR_API_KEY`, keeping the rest of the entry. That is the place the Cursor process, the probes, and the usage reader already read. Nothing is logged, noted, or echoed back, and no OpenClaw auth profile is created. It is not called `api-key`: OpenClaw gives that ID a quick entry that stores the key in its auth store instead.

Checked against OpenClaw 2026.10.3: the Control UI list is built from the manifest's `providerAuthChoices` (credential-only choices with `appGuidedAuth` or `appGuidedSecret`; `models.authStatus` shows them as `loginOptions`), and the login flow looks the method up in the registered provider (the provider-catalog entry's `auth` is not read; with only the manifest, the flow fails with `No provider plugins found`). The gateway's `models.authLogin` ends a method that returns no profile with `<label> did not return a credential profile.` after the report or the config write, so the dialog shows that message; `openclaw models auth login --provider cursor-cli --method login` ends cleanly. The live look at a real Control UI is the owner's check.

Provider card state (read from the OpenClaw 2026.10.3 Control UI and Gateway; a live Control UI look was not run): the card's credential line (`model-providers-page-*.js`) prints `Not configured` when the provider has no auth profile (OAuth or token), no API-key profile, no config key, and no env key; the status badge comes from `models.authStatus` (`models-auth-status-*.mjs`), whose `apiKey` summary is set only from `models.providers.<id>.apiKey` or the provider's env variables, and whose profile rollup reads the auth store. The card shows nothing the plugin supplies besides the provider ID. The manifest's `syntheticAuthRefs` and `nonSecretAuthMarkers` do not reach it: the marker list is read for bundled plugins only (`model-auth-markers-*.mjs`, `plugin.origin === "bundled"`), and synthetic auth serves model availability, not this summary. So there is no honest stop-gap: the login cannot be shown without a saved credential, and the plugin will not write a placeholder key to config or create a stand-in auth profile (it would change auth resolution, and a broken login would then look signed in). Upstream: [openclaw/openclaw#184700](https://github.com/openclaw/openclaw/issues/184700). `test/provider-card-limit.test.ts` pins the host facts, so a newer OpenClaw that changes them fails it and prompts a recheck.

Allow-list: an explicit `agents.defaults.modelPolicy.allow` must name `cursor-cli/*`, or direct selection is refused (see [Setup](../setup.md#3-configure)).

Icon: the package ships its own neutral icon (a terminal prompt and a block cursor, not Cursor's brand mark) as `assets/icon.png`, a 256x256 PNG. OpenClaw 2026.10.3 reads a plugin icon only from that fixed path (there is no manifest key), so the Gateway's `plugins.list` reports `hasIcon: true` for the plugin (`openclaw gateway call plugins.list`; `openclaw plugins inspect` prints no icon field in that version). It is one icon for the plugin, not one per CLI.

Where the Control UI shows it, and where it never does (read from the OpenClaw 2026.10.3 Control UI bundle; a live look in a headless browser was not run):

| Place | Plugin icon? | What decides it in OpenClaw |
| --- | --- | --- |
| Plugins page (cards and detail), command palette plugin entries, channel setup, the chat install card | Yes | These load `/__openclaw__/plugin-icon/<plugin id>` for every plugin whose `plugins.list` row has `hasIcon` (`plugin-icon-http-*.mjs`, `resolvePluginIconSource` in `management-service-*.mjs`; `plugins-page-*.js`, `command-palette-*.js`, `channels-page-*.js`, `control-ui-boot-chat-*.js`). |
| Model picker and provider cards | No: a letter avatar | The icon comes from a fixed set of brand SVGs bundled with the Control UI (`provider-icons/ProviderIcon-<provider id>.svg`), looked up by provider ID through an allow-list and alias map (`Lp`, `Gp`, `Kp` in `control-ui-boot-shared-*.js`). `cursor-cli` is not in it (`cursor` is), and no plugin file is read. |
| "Connect provider" list | No: a letter avatar | `model-setup-page-*.js` uses the same bundled set by provider ID, else the choice's `icon`. That is an HTTPS URL honored only when ClawHub catalog metadata registered it (`catalog-icon-registry-*.mjs`); OpenClaw's manifest docs call provider-auth artwork server-owned catalog metadata. A plugin installed from npm cannot set it. |

So the letter avatar in the model picker, on the provider card, and in the Connect provider list is OpenClaw's behavior for a provider ID it has no brand artwork for, not a missing file in the package.

## Models

`/model`, the model picker, and `openclaw models list --provider cursor-cli` show the models your Cursor account has, as `cursor-cli/<name>` with the readable name Cursor gives them:

```text
cursor-cli/auto
cursor-cli/composer-2.5
cursor-cli/grok-4.7
cursor-cli/claude-opus-5-5
```

The list comes from Cursor, never from the plugin. The plugin starts a short `cursor-agent acp` session in a temporary directory, reads the models Cursor reports in `session/new`, closes it, and removes that session's directory from Cursor's `acp-sessions` folder. When OpenClaw gives the plugin the agent directory (it does for the main agent's catalog), the listing's process is recorded in that agent's `pids/` like every other process (see Operations) and is stopped when the Gateway stops. No prompt is sent, so no model runs and no tokens are spent. The plugin reuses a listing for one minute (keyed on the command and the environment, so a changed `CURSOR_API_KEY` lists again at once; an account switch is noticed after the minute; from a logged-out state the next read lists at once, because nothing was cached) and lists again when OpenClaw next asks for its catalog (Gateway start, `openclaw models list --refresh`). A failed listing is remembered for 30 seconds, so a refresh within that time shows the failure again. A turn never waits for the list.

The picker and `openclaw models list` show each model's display name with the prefix `OAC / ` (for example `OAC / Auto`, `OAC / GPT-5.3 Codex`), the default model included, so these models stand apart from another provider's. Only the display name changes; the model ref (`cursor-cli/<name>`), ID, and aliases stay.

Cursor's own model IDs carry parameters, for example `grok-4.7[context=256k,reasoning_effort=high,fast=true]`. The name in the model ref is the base ID without the parameter list (`grok-4.7`), so it stays the same when Cursor changes a model's defaults. When several IDs share a base, the first one in Cursor's list keeps the bare name and the others get their parameter values as a suffix (`twin`, `twin-high`), then `key-value` pairs, then a number; `/model` labels each of them with its parameters. Names therefore follow Cursor's list order: a variant appended after the first changes nothing, but a variant added ahead of the first, a reorder, or the removal of the first moves the bare name (and the suffixed names after it) to another variant, and a configured `cursor-cli/twin` then runs that other variant. The plugin maps the name to Cursor's exact ID for you. You can also type the exact ID, in any case. `cursor-cli/default[]` and `cursor-cli/default` mean `cursor-cli/auto`.

| Situation | What happens |
| --- | --- |
| Logged in, or `CURSOR_API_KEY` set | The models are listed and available |
| Listing fails (`cursor-agent` missing, an error, no answer in 30 seconds) | Only `cursor-cli/auto` is listed and the failure is logged; no turn fails. The next listing attempt is at least 30 seconds later |
| Not logged in and no key | Only `cursor-cli/auto` is listed, as unavailable (`missing-auth` in the Gateway's raw model list). The default `openclaw models list --provider cursor-cli` then prints `No models found.` (checked on a fresh install with OpenClaw 2026.10.3). A turn fails with the login error. `openclaw models status` still says `[indeterminate]`: that command reads no prepared auth |
| A model the account does not have | The turn fails with `Cursor has no model "<name>" for this account` (error code `model_not_found`) |
| A model the plan cannot use | Cursor answers with its own plan message, for example `Upgrade your plan to continue`; the plugin does not filter it out |

Cursor keeps the model you last used in the agent's own config (`<agentDir>/openclaw-all-cli/cursor-cli/cli-config.json`), so every turn checks the session's model against the model ref. A turn on `cursor-cli/auto` switches back to Auto when the session starts on another model, and sends nothing when it is already on Auto. The exact ID is checked against the session's own list when the session starts, so a stale list cannot pick a model the account lost.

OpenClaw loads the plugin before the first turn only when your config names a `cursor-cli/...` model, for example as the default model. Until then the Gateway's model list has no Cursor rows.

Every model is declared to OpenClaw with `text` and `image` input, because the plugin sends images as ACP image blocks (P13, see Images), so OpenClaw routes image attachments to Cursor models.

### Context window

`openclaw models list --all` and the `/model` picker show a context window per model, and OpenClaw sizes its compaction by it. The plugin publishes the window it can ground, per model, and leaves the field out otherwise, so OpenClaw shows its own default (128k) only for those models:

| Model | Window shown |
| --- | --- |
| The Cursor ID has a `context=` value (`context=256k`, `context=1m`) | That value: `k` is 1,000 and `m` is 1,000,000 (`256k` is 256,000), so the smaller reading is used and compaction never comes late |
| No `context=` value, and the base model is `grok-4.7` (256k), `claude-opus-5-5` or `claude-opus-5` (300k) | That family's window, the one Cursor's listing gave for it |
| Anything else (Auto, `composer-*`, `gemini-*`, other models) | None published: OpenClaw's default applies. The plugin does not guess a window Cursor did not state |

A value that is not a number (`context=max`) is ignored. Effort variants of one model share their other parameters, so choosing an effort never changes the window. The window comes from the model list, so it follows Cursor's changes after the listing's one-minute cache (see above) and needs no setting. Live check (the numbers match the owner's Cursor account) not run: it needs a login.

### 1M context variants

Cursor sells some models with a 1M context: `cursor-agent --list-models` shows "Claude Opus 5.5 1M" and similar rows ([#46](https://github.com/xtimor/openclaw-all-cli/issues/46)). The plugin cannot offer them as `cursor-cli/...` models, because Cursor refuses them over ACP, the protocol the plugin talks. The 300k in `openclaw models list` is Cursor's ACP default for these models, not the models' limit.

Checked live 2026-10-28 (cursor-agent 2026.10.22, `CURSOR_API_KEY`, a throwaway config directory):

| Request | Answer |
| --- | --- |
| ACP `session/new` model list | 47 models; the Claude rows that carry a window have `context=300k` or `context=200k`, and none has `context=1m` |
| `session/set_model` and `session/set_config_option` with `claude-opus-5-5[context=1m,effort=medium,fast=false]` (the listed row's ID with `context=1m`) | `Invalid params`: `Invalid model value` |
| The same for `claude-opus-5[...]`, `claude-opus-4-8[...]`, `claude-sonnet-5-5[...]`, `gpt-5.6-sol[...]`, and spellings such as `context=1M`, `context=1000k`, `[1m]`, `claude-opus-5-5-1m`, the CLI's `claude-opus-5-5-medium` | All refused the same way |
| `cursor-agent --model 'claude-opus-5-5[context=1m,effort=medium,fast=false]' acp`, then the session | Starts, but reports the 300k row as its model (`currentModelId`); the launch flag does not select a 1M model over ACP |

The Cursor billing for a 1M turn is not shown by `cursor-agent`; the one turn above printed token counts only, so what a 1M turn costs is not known here. If a later Cursor version lists a `context=1m` row in the ACP session, the plugin shows it as its own model next to the 300k one (the first row of a base keeps the bare name; the 1M row gets its parameter values as a suffix, as for any variant) with a 1,000,000 window read from its own ID, and a 1,000,000 context ceiling for the usage check, with no change to the plugin.

### Effort

OpenClaw's Effort control (`/think`, the composer's effort picker) works for the models whose Cursor ID carries an effort setting: a `reasoning_effort=` or `effort=` parameter, as in `grok-4.7[context=256k,reasoning_effort=high,fast=true]`. Such a model is published as a reasoning model; every other model is published without reasoning, so the control does nothing there.

Cursor has no per-turn effort switch over ACP. The effort is part of the model ID, so the plugin maps the level onto an ID Cursor listed. When a turn opens its session, the plugin looks in Cursor's list for a model with the same base and the same other parameters (`context`, `fast`, and so on) whose effort value matches the level, and runs the turn on it:

| OpenClaw level | Cursor effort value |
| --- | --- |
| `off` | `none` or `off` |
| `minimal`, `low`, `medium`, `high`, `xhigh`, `max` | the same word |
| `adaptive` | none: the model you chose keeps its own effort |

No level set is not "keep the model's effort": OpenClaw 2026.10.3 then runs a reasoning model at its default level, `medium` (unless `thinkingDefault` or the model's `thinking` parameter in your config says otherwise), and that is the level the plugin gets. So `cursor-cli/<model>` with a listed `medium` variant runs on that variant until you pick another level. A level with no matching variant runs the model you chose, with its own effort. The plugin never invents an ID; Cursor refuses a model it did not list.

What Cursor does not offer:

- Effort can only be chosen among the variants Cursor lists. When the list holds one variant per model (the usual case in a plain account listing), the level cannot change anything, and the model keeps the effort in its ID. The Effort control still shows for that model.
- `/think` and the picker offer only `off` to `high` for these models: OpenClaw 2026.10.3 refuses `/think xhigh`, `max`, and `adaptive` for them. A Cursor `xhigh` or `max` variant is reached through its own model row.
- The level applies when the session opens. Changing it in a running chat starts a new Cursor process that resumes the same chat (the same restart as a model change, about 3 seconds).
- A side question runs with the level of the chat's run like any other turn.

## Operations

Limits, version floor, and cleanup for the `cursor-agent` processes the plugin starts.

- **Caps.** Per backend, at most `maxConcurrentTurns` turns run at once (default 4) and at most `maxProcesses` `cursor-agent` processes exist, idle ones included (default 8; at least `maxConcurrentTurns`). A turn over the cap waits its turn in order and starts when a slot frees. The plugin sets no timer for that wait: it ends when a slot is free or when OpenClaw aborts the turn, and OpenClaw's own no-output watchdog may end a long wait first. When the process cap is full, the least recently used idle process (or one that died while idle) is closed, and the new process starts once it has exited, waiting at most 3 seconds, so the cap holds except for a process that ignores the close past that grace. Both numbers sit under OpenClaw's global limit of 16 live sessions. Set them in the plugin config (see [Setup](../setup.md)).
- **Version check.** Before the first process of a command, the plugin runs `cursor-agent --version` and compares it with the minimum, 2026.07.06. An older build fails the turn with `unsupported_version`, naming the found and the required version and telling you to run `cursor-agent update`; no ACP session starts. A version the plugin cannot read (a failed or slow `--version`, unknown text) only logs a warning and the turn runs; the check repeats for the next process. A pass is remembered per command until the Gateway restarts. A missing binary fails the turn the same way as at spawn (`Could not find the CLI binary`).
- **Process groups.** Cursor starts a `worker-server` child (with `typescript-language-server` and `tsserver` children of its own) that outlives a `cursor-agent` stopped alone for about 5 minutes. So on Linux and macOS the plugin starts each `cursor-agent acp` as the leader of its own process group and stops the whole group wherever it stops the process: SIGTERM to the group, and SIGKILL to it after 2 seconds if any member is still there. That covers an idle close, an eviction, an abort, an unload, a failed start, and a `cursor-agent` that dies on its own (its group is stopped in the same moment). A close finishes, and the lock is released, once the leader has exited and the group is empty (checked every 100 ms), or the SIGKILL was sent. The plugin signals only a group whose leader it started itself. Ctrl-C in the terminal of a foreground Gateway no longer reaches `cursor-agent` directly; the Gateway's own stop closes it. Windows keeps the single-process behavior.
- **When a `worker-server` exists.** In a real install it starts at `session/new` but exits at once without its folder `projects/<slug>` under Cursor's data dir; Cursor creates that folder after the first turns, so the live tests create it by hand.
- **Orphans.** `cursor-agent acp` ignores a closed stdin and stays up when its Gateway is killed. The plugin writes `<home>/pids/<pid>.json` (mode 0600) for each process it starts, with the process and the Gateway's start times and `"group": true` when the process leads its group, and deletes it when the process exits. When a Gateway starts and loads the plugin it kills the processes recorded for the configured agents; any other agent's home is cleaned the first time it is used, before its first process opens. A process is killed (SIGTERM, then SIGKILL after 2 seconds) only when its recorded pid and start time still match and the Gateway that started it is gone; for a lock with `"group": true` the whole group goes, but only while the recorded leader is alive with the recorded start time and still leads its group (a dead or reused leader proves nothing about the group, so no group is signalled, and the SIGKILL needs the same proof again). A lock without `group` (written by an older plugin) stops the process alone. A lock whose Gateway is alive, or whose pid now belongs to another process, is left alone. Without `ps` nothing is recorded or killed, and the log says so.
- **Unload.** When the Gateway stops or the plugin reloads, every process of every backend is closed (its whole group, see above) and a model listing in flight is aborted; the stop waits (at most 3 seconds) for the exits. New turns after that fail with a retryable "shutting down" error.
- **Timers.** The plugin adds none. OpenClaw's no-output and overall watchdogs, and `--timeout`, abort the turn; the plugin then cancels Cursor and closes the process after a 5 second grace. A warm process closes after 15 idle minutes.
- **Clean environment.** OpenClaw removes the keys in the backend's `clearEnv` from the Gateway's environment before a turn, and the plugin removes the same keys for the model listing and the login check: Cursor endpoint overrides (`CURSOR_API_BASE_URL`, `CURSOR_API_ENDPOINT`, `CURSOR_WEBSITE_URL`), its harness and debug switches, `CURSOR_CONFIG_DIR` and `CURSOR_DATA_DIR` (the per-agent home sets them), `NODE_OPTIONS`, and the `OTEL_*` exporters. `OPENCLAW_ALL_CLI_CURSOR_USAGE_URL` (a test override of the usage ledger address) is removed too, so a Gateway environment cannot redirect the key. `CURSOR_API_KEY` and `CURSOR_AUTH_TOKEN` stay: they are logins.

### Capability check

Right after `initialize`, before the login, `session/new` or `session/load`, the plugin compares what `cursor-agent` reports with what the plugin's manifest needs. A miss fails the turn with `Capability mismatch: Cursor CLI does not report <what> (parity row Pn), which the plugin's manifest needs. Update the CLI.` (`capability_mismatch`, not retryable), closes the process, and sends no prompt. No chat is created or loaded, so a refused turn leaves no Cursor chat behind and never touches the chat you resume. If a transport only reports after it created a chat, the core closes the process and removes that new chat's directory (never a resumed chat's). The check runs for every process the plugin starts for a turn (agent turns and side questions, new and resumed chats), not for a reused warm process, and not for the throwaway session of the model listing. A CLI that reports more than the plugin needs passes. The mismatch is reported before later errors such as a stale model name.

| What | Row | Needs from `cursor-agent` |
| --- | --- | --- |
| Session resume | P5 | `agentCapabilities.loadSession` (a resume needs it even without the row) |
| HTTP MCP servers | P7 | `agentCapabilities.mcpCapabilities.http` (the MCP proxy is HTTP) |
| Image prompts | P13 | `agentCapabilities.promptCapabilities.image`, checked, as the row is decided (`approx`) |

Also checked at open: the login method. If `authMethods` lists methods and `cursor_login` is not one of them, the turn fails with `capability_mismatch` and the text `The CLI offered no "cursor_login" login method` (an empty list skips the login; an absent list logs in as before). Checks that already existed: the mode the turn needs must exist: `ask` for a side question or a turn without host `exec` (P18), `agent` when OpenClaw serves `exec`; a named model needs the CLI's model list (P1); an ACP protocol other than 1 and a build below the minimum version fail as `unsupported_version` (P19). Rows with no signal at open (P3, P4, P8, P10, P15, P16) are not checked; P6, P11, P12 and P14 have no mechanism in the core.

Real `cursor-agent` 2026.10.16 reports `loadSession`, `mcpCapabilities` with `http` and `sse`, and `promptCapabilities.image`, so it passes. Live test: `test/live/capability-check.live.test.ts`.

## Usage

Cursor's ACP reports no token counts, so the plugin reads them from Cursor's server-side usage ledger, the same numbers `cursor-agent -p` prints. Each model request is a ledger event keyed by the ACP session id.

After a turn ends with a result, the plugin exchanges `CURSOR_API_KEY` for a short-lived access token (`POST /auth/exchange_user_api_key`), then polls `POST /aiserver.v1.DashboardService/GetFilteredUsageEvents` for an event of the turn's session stamped inside the turn's time window. It puts `input` (Cursor's `inputTokens`, which excludes cache), `output`, `cacheRead`, `cacheWrite`, and their sum on the result (the sum is left out when it cannot be a context size, see below), and OpenClaw writes them on the assistant entry of its transcript. Two turns of one chat each get only their own event.

- **Needs `CURSOR_API_KEY`** in the Cursor process's environment: the plugin config `cursor-cli.env` (preferred, see [Setup](../setup.md#the-api-key)) or the Gateway's environment. The plugin reads the key from the same environment it starts `cursor-agent` with. With a login only, no usage is recorded and no request is made.
- **Where the key goes.** Only to `api2.cursor.sh`, the host `cursor-agent` already talks to. The key and the token stay in memory; no log line, warning, or file holds them, or a response body. Redirects are not followed.
- **Cost.** The ledger shows the event 2 to 6 s after the turn (measured 2026-10-21 over 60 turns: median about 3 s, slowest 6.2 s, independent of the pause between turns and of how often it is polled), so the turn closes about 2 to 4 s later, and at most 15 s later when the event does not appear (every request is cut at that deadline). The first poll comes 2 s after the turn, then one per second. The reply text has already streamed by then. A cancelled turn stops waiting at once.
- **The ledger is undocumented.** When it fails the reply still reaches OpenClaw, without usage:

| Situation | Result |
| --- | --- |
| No `CURSOR_API_KEY` | No usage, no request |
| Key rejected (exchange answers 401 or 403) | No usage; the ledger is skipped for this key for 10 minutes; one warning |
| Ledger answer changed (400, 404, 415, or an events field that is not a list) | No usage; 10 minutes off; one warning |
| Token expired (RPC answers 401) | Exchanged again once and retried; a second 401 counts as a rejected key |
| 5xx, 429, 403 from the ledger, network error, or a request over 6 s | Tried again at the next poll while time remains; then no usage for this turn, quietly |
| No event within 15 s (an answer with no events field counts as this), or three such failures in a row | No usage; after the third in a row, 10 minutes off and one warning |

- **Team accounts are untested.** The ledger may list nothing without a team id; such a turn ends like "no event" and the third in a row turns usage off for 10 minutes.
- **Behind an HTTP proxy.** Node's `fetch` ignores `HTTPS_PROXY` unless the Gateway starts with `NODE_USE_ENV_PROXY=1`. Without it the calls fail as network errors and usage stays 0.
- **Several events in one turn.** The turn's events already visible at the poll are summed; an event that appears after that poll is not added (no extra poll, to keep the latency). Cursor wrote one event per turn in every probe.
- **Host clock skew.** An event is matched by Cursor's timestamp against this host's clock with 5 s of slack. A host clock more than 5 s off makes usage silently 0 until the miss streak starts its 10 minute cooldown.
- **What the numbers mean.** They are the turn's totals, as Cursor bills them: `input` is new (uncached) prompt tokens, `cacheRead` and `cacheWrite` are prompt tokens served from or written to Cursor's cache, `output` is generated tokens, and the total is their sum. A turn with tool calls makes several model requests, and Cursor sums them into the one event, so the cached prompt is counted once per request (live, cursor-agent 2026.10.22: a plain turn of a short chat gave 164 input, 32 output, and 15 232 cache read tokens). cursor-agent 2026.10.22 still sends no usage over ACP; the ledger is the only source.
- **The context tile.** OpenClaw 2026.10.3 reads a CLI turn's `input + cacheRead + cacheWrite` as the size of the context the model saw: that is the "used" number of the Control UI's context tile, and what its `cli_budget` compaction compares with the budget. For a turn with one model request it is the context size; for a turn with several it is too high. When that reading plus `output` (or the total) is more than the model's context window, no single request could have held it, so the plugin drops the total and tells OpenClaw the turn's context size is unknown (OpenClaw's `contextUsage: unavailable` marker). The token counts stay as reported. OpenClaw then keeps no context reading from that turn: the tile shows the earlier reading with `~` in front, or nothing, and compaction uses its own transcript estimate. The window is the model's own (see [Context window](#context-window)); for Auto and for a model without a known window it is the largest window among the account's models. A sum over several requests that stays under the window still shows, too high (issue [#40](https://github.com/xtimor/openclaw-all-cli/issues/40)).
- **Rare overlap.** A turn never counts an event Cursor stamped at or before the last event an earlier turn of its chat consumed. Beyond that, the lower bound is the earlier turn's end minus the 5 s skew slack, so if that earlier turn's lookup found nothing and the next turn starts within the slack, the next turn can also count the earlier event (an overcount is chosen over dropping the next turn's usage when the clocks differ). The record is in memory (bounded to 1000 chats) and lost on a Gateway restart, so the first turn after a restart can count an older event of the same chat inside the 5 s window.

Live test: `test/live/usage.live.test.ts`.

| P17 | Clean env, watchdog, timeouts | match | OpenClaw's watchdog and timeouts end a turn through its abort signal and the plugin adds no timer; `clearEnv` drops endpoint, harness, debug, and telemetry keys; per backend 4 turns and 8 processes by default; a pid lock per process and reaping of a killed Gateway's orphans; every process closed on unload. See Operations. Live test: `test/live/operations.live.test.ts` |
| P18 | Side questions without tools | approx | A side question runs in `ask` mode with no MCP server, no resume, and every permission request rejected; no OpenClaw tool, shell, or write. | P19 | Binary detection, live tests | approx | OpenClaw finds `cursor-agent` on `PATH`; the plugin checks `cursor-agent --version` against the minimum 2026.07.06 before the first process and fails the turn below it (`unsupported_version`). ## Known limits

- **The continuity note can be lost with a failed first prompt.** The plugin marks a chat as fresh in memory and clears the mark before the first prompt runs. If that prompt fails before Cursor stores it, the next turn resumes the chat without the note.
- **A side question takes a turn slot.** A side question, or any nested turn, holds a turn slot like every other turn: with `maxConcurrentTurns` 1 it waits for the running turn.
- **What can still remain after a stop.** The plugin promises this much and no more. Each item has its bound:
  1. A Gateway killed with SIGKILL leaves its `cursor-agent` groups running until the next Gateway start reaps them (within 30 seconds of that start for the agents the config names; any other agent's home is cleaned at its first use).
  2. A group whose leader died while no Gateway ran is not reaped, because nothing proves its members are the plugin's. Its `worker-server` exits by itself about 5 minutes after its last request. The same holds in the reaper when the leader exits on SIGTERM and a member ignores it.
  3. A `worker-server` shared by two plugin processes (same agent and workspace; or Cursor's `/tmp/.cursor` fallback for long paths, where it may also be shared with your own `cursor-agent`) dies with the process that started it. The other process starts a new one on its next request, so only the worker's cache (language-server state, indexing) is lost.
  4. Children Cursor puts in a process group of their own (its native shell does; the plugin's static home denies that shell) are not covered.
  5. Windows has no group handling: a `worker-server` can outlive its `cursor-agent` for about 5 minutes.
  6. A new chat Cursor refuses after `session/new` (an unknown model, a missing mode) keeps its `acp-sessions` directory (a few kilobytes).
  7. A model listing for which OpenClaw gives no agent directory is not recorded (the log warns once); a Gateway killed in its few seconds can leave that process behind, and no later start reaps it.
  8. A Gateway ended by a signal that skips its stop (for example SIGHUP) leaves the groups until the next start; groups are detached, so a closed terminal no longer reaches `cursor-agent`.
  9. A side question running when the Gateway is killed or crashes keeps its `acp-sessions/<id>` directory (also when the discard fails or the 3 s unload wait ends first); a listing aborted after `session/new` keeps its directory too. These directories stay until removed by hand; the reaper removes none.
  10. A listing in another host thread that answers the unload later than the 150 ms window, or whose worker thread the host ends, is not stopped until the next start's reap.
  11. The lock is released when the SIGKILL has been sent, not when the members have exited. Members that remain after the SIGKILL, if any, have no lock and no later start reaps them; they exit by themselves within about 5 minutes.
  12. Under a PID 1 that never reaps (a container without an init), zombie group members delay each close by up to the 2 s grace, and the start-up reaper waits the full grace per lock and logs "Part of the process group ... is still running" for zombie members.
- **A webchat may draw the reply twice.** Seen as a report, not reproduced here. The plugin sends the reply once as streamed text and once as the closing record's text, and the host turns the second into the turn's final text only, so the plugin cannot remove a duplicate bubble without dropping the reply. If it shows, it comes from how the Control UI joins the host's deltas, `final`, and `assistant` snapshot (openclaw/openclaw#180927). See Streaming and tool progress.
- **No separator around a tool call.** Cursor's message chunks carry no break between the text before and after a tool call, so a reply can read `...sentence.Next text`. The plugin passes the text through unchanged.
- **Usage and a skewed clock.** A host clock more than 5 s off Cursor's makes usage 0 until the cooldown (see Usage).
- **Usage needs an API key.** With a Cursor login only (no `CURSOR_API_KEY`), OpenClaw records 0 tokens for a turn. See Usage.
- **The context tile can read too high, or show `~`.** Cursor's usage is a sum over the turn's model requests, and OpenClaw reads it as the context size. Above the model's window the plugin marks it unknown and the tile keeps the earlier reading with `~`; below the window a turn with tool calls still reads high. See Usage.
- **HEIC, AVIF, SVG, TIFF, and empty images are not sent.** They get a one-line note. See Images.
- **No image delivery on Windows.** Without a process uid the plugin cannot check file owners, so it leaves the prompt as it is. See Images.
- **A CLI without image support fails every turn.** `capability_mismatch` at open, text-only turns too (by design). See Capability check.
- **Compaction replaces the Cursor chat.** After `/compact` (and, unverified, a budget compaction) the next turn is a fresh Cursor chat: Cursor's own context, including earlier images, is gone. The model reads the summary through `sessions_history`. Without an API compaction model, compaction fails. See Compaction.
- **Cursor's own summarization is not visible.** Cursor may summarize a long chat server-side; ACP shows nothing of it and offers no way to trigger it.
- **Cursor may shorten the system prompt.** The block lives in Cursor's chat. If Cursor summarizes a long chat, the instructions may be shortened until the prompt changes. Nothing detects this.
- **A stopped turn costs a block.** A turn that errors, crashes, or is aborted records no delivery, so the next turn resends the block (about 8,000 tokens in Cursor's chat each time).
- **Copies of the block add to the chat's size.** OpenClaw's `cli_budget` compaction takes the larger of its transcript estimate and the session's total tokens from usage, which counts every block copy in Cursor's chat. With an API key a long chat can reach the budget sooner; with no API model or Cursor API-key profile the compaction then fails the turn.
- **Cursor's own instructions and skills load too.** Cursor reads `AGENTS.md`, `CLAUDE.md`, and `.cursor/rules` in the workspace, and skills in the workspace and in your home's dot directories (`~/.cursor/skills`, `~/.claude/skills`, `~/.agents/skills`, `~/.codex`, `~/.grok`), and the plugin cannot switch that off. The workspace `AGENTS.md` is seen twice, and a skill of yours can appear in both lists.
- **A turn in the first seconds after the Gateway starts restarts the process once more.** OpenClaw 2026.10.3 decides whether a turn gets the tools `computer` and `view_image` from the `input` of the model's row in its Gateway-wide model catalog, and that catalog holds the plugin's `cursor-cli` rows only after the plugin's listing (about 4 s of ACP) has finished. A turn that starts earlier gets 50 tools and the next one 52, and the system prompt lists the two tools too. OpenClaw hashes the tool names and the system prompt into its live-session check, so the second turn restarts the process and resumes with `session/load` (log: `reuse=reusable-drift:prompt-tools`); it costs about 3 s once. Once the catalog has loaded, a new agent keeps one process from its first turn (live test), and a plain config write does not unload it. The plugin cannot close the gap: the chat path of OpenClaw reads only the loaded catalog (an `openclaw agent` run also reads plugin manifests, but the web chat does not). A model row in your own config (`models.providers.cursor-cli.models`, with `input: ["text", "image"]`) makes both paths see the same tools from the first turn, for the models it lists; the plugin does not set it for you. The system prompt also changes once more when OpenClaw deletes the agent's first-run file `BOOTSTRAP.md` (it does so by itself once the workspace shows user content, such as a `memory/` folder, a `MEMORY.md`, a skill, or an edited `IDENTITY.md`, `USER.md`, or `SOUL.md`), which restarts the process once.
- **The first reply of a new session can take 20 s or more.** Mostly the model thinking over the agent's instructions, plus about 4 s of process start and `session/new`; the plugin keeps no spare process or prepared chat. See First reply of a new chat.
- **Native read, grep, and glob stay reachable, also in a side question.** `Read(**)` is allowed, and Cursor's `grep` and `glob` are not blocked by a `Read` rule. So a run that selects no native tools is refused (see Permissions and tool availability). A second, static home that also denies `Grep(**)` and `Glob(**)` would lift this (checked: those rules make grep and glob return nothing); it is not built.
- **Agent mode is token-hungry.** A turn with host `exec` runs in agent mode and can use many tokens (tool calls the model tries, then Cursor blocks). When OpenClaw's `cli_budget` compaction then runs and has no API model to summarize with, the turn fails with `CLI transcript compaction failed for cursor-cli/auto`. Seen once in the live suite (not reproduced on a re-run). A Cursor API-key profile or an API model for compaction avoids it.
- **Shell limits.** `exec` calls are stopped at 55 s, a rooted or exec-host-`node` run has no `exec` (a capped run is refused), and commands can read the Gateway's environment. See Shell commands (OpenClaw exec).
- **A reply that is exactly such a final chunk reads as an error.** A model answer whose last chunk starts with a blank line and `Error: <Name>: ` or `Error: [code]`, or is one of the four phrases above on its own, becomes an error turn.
- **A quoted `403` or `401` makes the host read an auth failure.** The host classifies by message text, and Cursor's own text is kept in it. A proxy refusal such as `HTTPS proxy CONNECT failed: 403 Forbidden` therefore reaches the host as `reason=auth` (seen live) although the plugin's class is `server_error`.
- **Native edits are never approved by the host.** Cursor cannot ask before editing.
- **Permissions are not configurable.** Every agent gets the same rules; changing them in `cli-config.json` has no lasting effect.

## Check it works

Follow [Setup, Verify](../setup.md#5-verify): the plugin is loaded, your Cursor models are listed, and `openclaw agent --model cursor-cli/auto` answers. Contributors also have a live test suite; see Develop in [Setup](../setup.md#develop). The live suite holds one test per decided parity row (the row ids are in the test titles; `test/parity-suite.test.ts` fails when a row, this table, the parity matrix, and the manifest disagree) and one scenario for the spec's success signal: an API-model turn, then a `cursor-cli` turn on the same chat that finds the earlier fact with `sessions_history`, runs a command through OpenClaw's `exec`, streams to the Gateway's operator clients, and reports Cursor's usage, beside a second agent, with both agents' workspaces unchanged (`test/live/success-signal.live.test.ts`; it needs `CURSOR_API_KEY`). `npm test` also runs host-contract tests against OpenClaw's own code when the isolated OpenClaw is installed.
